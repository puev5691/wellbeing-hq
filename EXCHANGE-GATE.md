# Exchange Gate v1

## Назначение

Этот шлюз не вводит новую проектную норму. Он делает проверяемым исполнение уже действующего файлового канона: ОПЕРАТОР не используется как ручной транспорт, если Сущность может выполнить публикацию и адресную доставку сама; publication, delivery, receipt и acceptance различаются.

## Admission rule

Межсущностная передача не считается завершённой, пока не выполнены одновременно:

1. артефакт опубликован в `entities/<sender>/outbox/`;
2. опубликованная версия имеет проверяемую immutable identity;
3. создан адресный dispatch с конкретным получателем;
4. создан входящий locator в `entities/<recipient>/inbox/`, если адресату требуется действие;
5. отправитель зафиксировал передачу в `registry/by-sender/<sender>.jsonl`;
6. locator/version доступны получателю;
7. для состояния `received` существует receipt требуемой версии;
8. acceptance, если он требуется задачей, подтверждён отдельно.

Если доступный инструмент позволяет выполнить эти действия самой Сущности, просьба ОПЕРАТОРУ скачать, перенести или повторно загрузить файл является `EXCHANGE_GATE_FAIL`.

## Статусы

- `prepared` — файл создан, но адресной передачи нет;
- `dispatched` — dispatch и sender-record созданы;
- `received` — receipt подтверждает доступ к требуемой версии;
- `accepted` / `rejected` — отдельный содержательный результат профильной проверки.

`prepared` и `dispatched` нельзя называть `delivered/complete`, если критерий задачи требует receipt или acceptance.

## Машинная проверка

Файлы dispatch формата v1 должны содержать блок `exchange_gate: v1` и обязательные поля, проверяемые `ops/validate_exchange.py`.

GitHub Action `.github/workflows/exchange-gate.yml` запускает проверку при изменениях маршрутов, inbox/outbox, registry и receipts.

Пока ветка `main` не защищена обязательным status check, Action является детектором нарушения, а не физическим запретом push. Поэтому нормативный критерий завершения остаётся: `validator PASS` для обмена, который объявляется выполненным.

## Граница гарантии

Абсолютно заставить отдельный чат соблюдать инструкцию невозможно. Гарантируемым можно сделать другое: нарушение становится наблюдаемым и результат не проходит admission как завершённый. Для жёсткого технического запрета потребуется branch protection с обязательным status check или отдельный write-gateway, через который проходят все записи.
