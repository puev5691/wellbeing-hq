## Что произошло

Подготовлен минимальный implementation candidate литературного журнала проекта.

Его задача — сохранить человеческую память о развитии «БЛАГОПОЛУЧИЯ»: значимые повороты, причины решений, неудачи и выводы, характерные эпизоды, полезные наблюдения и человеческий контекст, который обычно исчезает, если сохранять только commits, terminal results и технические отчёты.

Кандидат не активирует журнал. Он только определяет простую рабочую форму, которую можно будет включить отдельным решением ОПЕРАТОРА.

## 1. Рекомендуемое место хранения

После отдельного activation decision использовать редакторское рабочее пространство RED:

`entities/redaktor/current/literary-journal/`

Минимальный набор:

1. `RED__project-literary-journal.md` — один долговременный основной журнал;
2. при реальном разрастании материала в будущем допускается разделение на тематические или периодические части, но только когда один файл объективно становится неудобен.

На старте одного долговременного файла достаточно.

Журнал не помещается в baseline Project Sources и не становится authoritative current-state.

## 2. Простая структура долговременного файла

Рекомендуемая структура:

- короткое назначение и truth boundary;
- раздел «Новые записи» в обратном хронологическом порядке поступления материала либо по естественной последовательности событий;
- при накоплении большого объёма — простой тематический указатель;
- никаких обязательных таблиц, JSON-схем и служебных карточек на каждое событие.

Главный принцип: журнал должен быть удобен человеку, который позже готовит статью, Telegram-публикацию, страницу портала или главу книги.

## 3. Минимальная форма одной записи

Одна запись может выглядеть так:

### <Короткое человеческое название эпизода>

**Что произошло.**  
2–5 предложений обычным русским языком.

**Почему это важно.**  
Что изменилось в проекте, понимании проблемы или направлении работы.

**Человеческая деталь.**  
Реплика, наблюдение, характерный эпизод, неожиданность, ошибка, сомнение или контекст, который делает событие живым и понятным.

**К чему это привело.**  
Какой следующий шаг, идея, правило, архитектурное изменение или новое направление возникло.

**Evidence при необходимости.**  
Один или несколько exact locator/immutable identities, достаточных для проверки фактической основы.

Не все пять подзаголовков обязательны буквально. Это ориентир, а не schema. Если запись естественно читается одним плотным абзацем и при этом сохраняет эти смыслы, этого достаточно.

## 4. Как отбирать значимые события

Запись создаётся только если событие имеет хотя бы один из признаков:

- изменило направление работы;
- породило новую архитектурную идею;
- выявило существенную ошибку или ложное предположение;
- привело к новому правилу/границе;
- закрыло значимый этап;
- открыло новый крупный фронтир;
- содержит важный человеческий контекст, который невозможно восстановить из machine evidence;
- представляет характерный или литературно ценный эпизод;
- объясняет, почему позднее проект устроен именно так.

Не являются достаточным основанием сами по себе:

- очередной commit;
- обычный PASS;
- routine terminal result;
- технический refactor без исторического следствия;
- повторяющееся операционное действие;
- любой task только потому, что он завершился.

## 5. Как накапливать материал без per-task reporting

Модель накопления: `episodic + periodic editorial sweep`.

### Episodic

RED добавляет запись, когда:
- произошёл явно значимый эпизод;
- ОПЕРАТОР прямо указал сохранить его;
- есть риск потерять ценную человеческую деталь;
- несколько технических событий сложились в один содержательный поворот.

### Periodic editorial sweep

Время от времени, когда это оправдано редакционной работой, RED просматривает уже существующие human-facing results и выделяет 1–3 действительно значимых эпизода, которые стоит сохранить.

Никакой обязательной календарной периодичности нет.

Нет правила «одна задача = одна запись».

## 6. Использование для Telegram, портала и книги

### Telegram

Журнал служит банком:
- коротких историй;
- неожиданных открытий;
- ошибок и уроков;
- объяснений «почему мы сделали именно так»;
- человеческих эпизодов.

Перед публикацией создаётся отдельная public/editorial task. Запись журнала сама по себе не считается готовым постом.

### Информационный портал

Журнал может быть источником human-readable history, causal context и объяснений развития направлений.

Exact machine provenance при необходимости показывается отдельным слоем, а не смешивается с основным текстом.

### Будущая книга / большая история проекта

Журнал хранит то, чего обычно нет в Git history:
- причины;
- сомнения;
- поворотные решения;
- человеческие реплики;
- неудачи;
- изменения взглядов;
- связь между проблемой и последующей архитектурой.

При подготовке книги записи проверяются против exact evidence там, где утверждается технический факт.

## 7. Technical evidence без машинного шума

Правило:

> journal text хранит человеческий смысл; GitHub хранит доказательство.

Если technical evidence нужно для проверки записи, достаточно указать:

- exact artifact/path;
- commit/blob/tree либо другой immutable identity;
- при необходимости короткое пояснение, что именно этот evidence подтверждает.

Не копировать в журнал:
- длинные manifests;
- hashes всех файлов;
- route history;
- полные logs;
- полный terminal report;
- machine statuses, если они не нужны для понимания сюжета.

## 8. Прямая цитата и пересказ

### Прямая цитата

Допустима только если:
- точная формулировка действительно важна;
- доступен проверяемый источник, содержащий эту реплику;
- цитата воспроизведена без смысловой реконструкции.

В журнале её следует явно обозначать как цитату и при необходимости дать source locator.

### Пересказ

Если точная формулировка не нужна либо дословный источник не сохранён, используется обычный пересказ без кавычек.

Нельзя восстанавливать «красивую» дословную речь по памяти или по смыслу и оформлять её как цитату.

## 9. Privacy / publication boundary

Журнал внутренний по умолчанию.

Не включать или не раскрывать без отдельного основания:
- credentials/secrets;
- чувствительные персональные данные;
- приватные данные третьих лиц;
- лишние runtime/config details;
- сведения, публикация которых не была отдельно разрешена.

Наличие записи в журнале:
- не делает материал public-ready;
- не даёт publication authority;
- не означает legal/privacy approval.

Любой выход во внешний Telegram, портал, статью, выступление или книгу проходит отдельную редакционную/public boundary.

## 10. Помощь ARH и KOO без смены владельца

### RED

Владелец литературного содержания и отбора записей.

### ARH

Может:
- сохранять snapshots/provenance журнала;
- помогать с recovery сохранённой версии;
- подтверждать существование/identity historical journal artifact.

Не становится автором повествования и не определяет, что литературно значимо.

### KOO

Может:
- маршрутизировать RED сведения о значимых проектных событиях;
- включать journal maintenance как bounded editorial work, когда это оправдано;
- связывать journal с задачами Telegram/портала/истории.

Не обязан писать журнал и не меняет editorial ownership.

## 11. Continuity при замене RED-чата

Journal continuity не должна зависеть от памяти текущего RED-чата.

После activation:
- долговременный journal artifact хранится в `entities/redaktor/current/literary-journal/`;
- replacement RED получает exact locator журнала через обычный recovery/current-state контур;
- recovery должен сохранять locator/identity текущего journal artifact как часть редакторской continuity, но сам журнал остаётся non-authoritative для technical state;
- новый RED продолжает существующий artifact, а не реконструирует литературную память по правдоподобию.

Если journal artifact недоступен или identity не совпадает, replacement RED не придумывает утраченные записи.

## 12. Truth boundary

Литературный журнал никогда не является доказательством:
- текущего technical state;
- task completion;
- delivery/receipt/acceptance;
- writer authority;
- deployment;
- production readiness;
- Project Source status.

Для технического утверждения authoritative evidence остаётся в проектном информационном поле.

Journal может объяснять **как и почему** развивался проект, но не заменяет доказательство **что именно технически истинно сейчас**.
