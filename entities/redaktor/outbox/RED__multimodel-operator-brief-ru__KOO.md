# Многомодельный шлюз — операторская версия

Статус: `WAITING_OPERATOR_EXTERNAL_PROVIDER_PILOT_DECISION`

## Что такое `multi-model gateway`

В нашей архитектуре `multi-model gateway` — многомодельный шлюз: промежуточный программный слой между проектом и внешними моделями.

Он должен:
- принять задачу;
- проверить разрешённый класс данных и допустимый маршрут;
- отправить задачу только разрешённой модели;
- зафиксировать происхождение результата;
- не позволить ответу модели автоматически стать решением проекта.

Для более сложного режима предусмотрены две машинные роли:
- **АВТОР** (`AUTHOR`) — создаёт кандидат результата;
- **ПРОВЕРЯЮЩИЙ** (`VERIFIER`) — независимо проверяет этот кандидат.

После этого отдельный этап сопоставляет результаты.

Даже полное согласие АВТОРА и ПРОВЕРЯЮЩЕГО не даёт им права самостоятельно назначить результат принятым, текущим или каноническим для проекта.

## Что уже реально сделано и проверено локально

КОДЕР реализовал локальный макет шлюза без внешних провайдеров.

Проверенная логика:

**описание задачи → проверка ограничений → локальный имитатор АВТОРА → отдельный локальный имитатор ПРОВЕРЯЮЩЕГО → сопоставление → неизменяемая запись происхождения результата.**

Проверено:
- компиляция: PASS;
- тесты: **18/18 PASS**;
- сеть не использовалась;
- внешние API не вызывались;
- учётные данные отсутствовали;
- реальные данные проекта модели не передавались;
- стоимость: 0;
- внешние инструменты и поиск были запрещены;
- резервное переключение на другую модель или маршрут было запрещено;
- при несогласии АВТОРА и ПРОВЕРЯЮЩЕГО расхождение сохраняется;
- результат не может сам отметить себя как принятый, текущий или канонический.

Статус локального макета:

`PASS_LOCAL_SYNTHETIC_GATEWAY_MOCK`

Этот статус подтверждает только локальную механику шлюза. Он не разрешает подключение реального внешнего провайдера.

## Что означает `D0_SYNTHETIC`

`D0_SYNTHETIC` — класс полностью искусственных тестовых данных.

В первый внешний пилот разрешается отправлять только специально придуманный тестовый материал, который:
- не содержит данных проекта;
- не содержит частной информации;
- не содержит секретов;
- не является рабочим документом;
- не требует доступа к файлам, поиску, внешним инструментам или подключённым сервисам.

Смысл первого пилота: проверить внешний маршрут без риска для содержимого проекта.

## Зачем разделять АВТОРА и ПРОВЕРЯЮЩЕГО

Если одна и та же модель сначала создаёт ответ, а потом сама подтверждает его правильность, независимость проверки слабая.

Разделение ролей позволяет:
- хранить кандидат и проверку отдельно;
- видеть согласие и несогласие;
- не скрывать расхождения;
- фиксировать точные модель и провайдера каждой роли;
- не позволять двум моделям совместно объявить свой ответ решением проекта.

При этом самый первый реальный внешний вызов может проверять только один прямой маршрут. Полная внешняя схема АВТОР + ПРОВЕРЯЮЩИЙ не обязана включаться в первый вызов класса `D0_SYNTHETIC`.

## Чем прямой маршрут отличается от маршрутизатора

### Прямой маршрут

Пример Anthropic:

`project gateway/client → api.anthropic.com → Anthropic Messages API → exact Claude model ID`

В этом случае проект обращается непосредственно к выбранному провайдеру и конкретной модели.

Для Google рассматривается аналогичный прямой управляемый путь через Google Cloud к конкретной Gemini-модели.

### Маршрутизатор или агрегатор

Пример:

`project gateway/client → OpenRouter API → pinned model → upstream provider endpoint`

Здесь появляется дополнительный слой `OpenRouter`, а за ним находится фактический поставщик модели.

Поэтому приходится отдельно доказывать:
- куда именно ушёл запрос;
- какая модель и какой фактический провайдер были зафиксированы;
- что резервное переключение отключено;
- что маршрут не может молча уйти к другому провайдеру;
- что политика хранения и обработки подтверждена не только для `OpenRouter`, но и для фактического внешнего провайдера.

То есть маршрутизатор удобнее для переключения моделей, но доказательная цепочка у него длиннее.

## Почему Anthropic и Google допущены как первые кандидаты

КАНЦЕЛЯР проверил свежие официальные сведения для трёх вариантов.

### Anthropic

Прямой коммерческий маршрут через API классифицирован:
- `ELIGIBLE_D0`;
- `ELIGIBLE_D1`.

Для рассматриваемого маршрута требуются:
- прямой `api.anthropic.com`;
- коммерческий/API-аккаунт, а не потребительский Claude;
- точный `Claude model ID`;
- без Files API;
- без серверных инструментов, поиска и выполнения кода;
- без отправки обратной связи;
- без данных выше разрешённого класса.

### Google

Прямой управляемый маршрут Google к Gemini также классифицирован:
- `ELIGIBLE_D0`;
- `ELIGIBLE_D1`.

Для него требуются:
- управляемый маршрут Google Cloud, а не потребительский Gemini;
- точный `Gemini model ID`;
- явная региональная или юрисдикционная точка подключения;
- журналирование запросов и ответов выключено;
- поиск и привязка к Google Search/Maps выключены;
- сохранение взаимодействий выключено;
- восстановление сессий выключено;
- внешние инструменты выключены.

### Почему `OpenRouter` пока условный

Для синтетического D0 маршрут через `OpenRouter` допустим только при жёсткой фиксации настроек, включая:
- одну точную модель;
- один точный фактический внешний маршрут;
- `allow_fallbacks=false`;
- отсутствие списка резервных моделей;
- `data_collection=deny`;
- предпочтительно `zdr=true`;
- `router_metadata=on`;
- отсутствие инструментов, файлов и кеша.

Для D1 его статус пока:

`CONDITIONAL`

Причина: сведений самого `OpenRouter` недостаточно. Нужна отдельная официальная доказательная база для фактического внешнего провайдера и проверка того, что настройка маршрута не позволит незаметно переключиться на другой путь.

Поэтому Anthropic и Google сейчас являются **допущенными кандидатами по имеющимся доказательствам**, но не выбранными и не авторизованными провайдерами.

## Что именно будет первым реальным пилотом

Первый внешний пилот должен быть предельно узким:
- только `D0_SYNTHETIC`;
- один прямой провайдер;
- одна точная модель;
- одна точная точка API;
- без резервного переключения;
- без инструментов;
- без поиска;
- без подключённых сервисов;
- без файлов;
- без рабочих данных проекта.

Задача первого пилота: доказать, что шлюз способен выполнить контролируемый внешний вызов по заранее известному маршруту и сохранить точное происхождение результата.

Это ещё не проверка всей будущей многомодельной системы.

## Какие данные в первый пилот передавать запрещено

Запрещены:
- любые реальные рабочие материалы проекта;
- приватные документы;
- персональные данные;
- секреты, токены, ключи и пароли;
- данные классов D2 и выше;
- содержимое подключённых сервисов;
- файлы проекта;
- любые данные, для которых внешний маршрут ещё не утверждён.

Также не разрешены поиск, внешние инструменты, подключаемые сервисы и автоматическое резервное переключение.

## Какое решение требуется от ОПЕРАТОРА

После чтения нужно выбрать **ровно один** вариант:

- `AUTHORIZE_ANTHROPIC_D0_PILOT`
- `AUTHORIZE_GOOGLE_D0_PILOT`
- `HOLD_EXTERNAL_PROVIDER_PILOT`

Это не выбор лучшей модели вообще и не архитектурный стандарт на будущее.

Это только решение о первом синтетическом внешнем маршруте.

`OpenRouter` как первый реальный маршрут сейчас не предлагается.

## Что разрешит такое решение

Если ОПЕРАТОР выберет Anthropic или Google, разрешается только подготовить и подключить точный путь пилота D0 для выбранного прямого провайдера в уже заданных границах.

Такое решение само по себе не разрешает:
- D1;
- D2 и выше;
- производственное использование;
- передачу данных проекта;
- произвольные подключённые сервисы;
- поиск;
- внешние инструменты;
- резервное переключение;
- автоматическое принятие ответа модели;
- покупку или подписку сверх отдельно подтверждённого действия;
- назначение провайдера постоянным стандартом проекта.

## Какие этапы возможны после D0

После успешного D0 можно отдельно рассматривать:
1. повторяемость внешнего маршрута и проверку фактического результата;
2. внешний режим АВТОР + независимый ПРОВЕРЯЮЩИЙ;
3. ограниченный класс D1 при сохранении всех разрешённых условий;
4. сравнение нескольких прямых провайдеров;
5. контролируемый D0 через `OpenRouter` с жёстко зафиксированным фактическим провайдером;
6. только после отдельных проверок — обсуждение более чувствительных классов данных.

Ни один следующий этап не становится автоматически разрешённым после D0.
