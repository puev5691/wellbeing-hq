# Multi-model — операторская версия

Статус: `WAITING_OPERATOR_EXTERNAL_PROVIDER_PILOT_DECISION`

## Что такое multi-model gateway

В нашей архитектуре multi-model gateway — это промежуточный программный слой, который получает задачу, проверяет разрешённый класс данных и маршрут, отправляет её выбранной модели, фиксирует происхождение результата и не даёт ответу модели самовольно превратиться в решение проекта.

Для более сложного режима предусмотрено разделение ролей:

- **АВТОР** (`AUTHOR`) — создаёт кандидат результата;
- **ПРОВЕРЯЮЩИЙ** (`VERIFIER`) — независимо проверяет кандидат;
- затем отдельный этап сопоставляет результаты.

Даже совпадение АВТОРА и ПРОВЕРЯЮЩЕГО не означает автоматического принятия результата проектом. Принятие остаётся отдельным действием уполномоченного участника.

## Что уже реально сделано и проверено

КОДЕР реализовал локальный макет gateway без внешних провайдеров.

Проверенная цепочка:

`task envelope → policy guard → fake author provider → independent fake verifier provider → reconciliation → immutable provenance`

По-русски:

**описание задачи → проверка ограничений → локальный имитатор АВТОРА → отдельный локальный имитатор ПРОВЕРЯЮЩЕГО → сопоставление → неизменяемая запись происхождения результата.**

Проверено:
- компиляция: PASS;
- тесты: **18/18 PASS**;
- сеть не использовалась;
- внешние API не вызывались;
- учётные данные отсутствовали;
- реальные данные проекта модели не передавались;
- стоимость: 0;
- внешние инструменты, поиск и fallback были запрещены;
- результат не может сам отметить себя как принятый, текущий или канонический;
- при несогласии АВТОРА и ПРОВЕРЯЮЩЕГО расхождение сохраняется и уходит на человеческое/координационное решение.

Статус локального макета:

`PASS_LOCAL_SYNTHETIC_GATEWAY_MOCK`

Это подтверждает механику локального контура, но **не разрешает** подключение реального провайдера.

## Что означает `D0_SYNTHETIC`

`D0_SYNTHETIC` — класс полностью искусственных тестовых данных.

В первом внешнем пилоте разрешается отправлять только специально придуманный тестовый материал, который:
- не содержит данных проекта;
- не содержит частной информации;
- не содержит секретов;
- не является рабочим документом;
- не требует доступа к файлам, поиску, подключаемым сервисам или инструментам.

Смысл первого пилота простой: проверить **сам внешний маршрут**, не рискуя содержимым проекта.

## Зачем разделять АВТОРА и ПРОВЕРЯЮЩЕГО

Если одна и та же модель сначала создаёт ответ, а потом сама же подтверждает его правильность, независимость проверки условна.

Разделение ролей позволяет:
- хранить отдельно исходный кандидат и проверку;
- видеть согласие или несогласие;
- не скрывать расхождения;
- фиксировать точную модель/провайдера каждой роли;
- не позволять двум моделям совместно «назначить» свой ответ решением проекта.

Первый реальный внешний вызов, однако, может проверять только **один прямой маршрут**. Полная внешняя схема АВТОР + ПРОВЕРЯЮЩИЙ не обязана включаться в самый первый D0-вызов.

## Прямой провайдер и маршрутизатор — в чём разница

### Прямой маршрут

Пример:

`project gateway/client → api.anthropic.com → Anthropic Messages API → exact Claude model ID`

или прямой управляемый маршрут Google к конкретной Gemini-модели.

Здесь основной внешний путь известен заранее: проект обращается непосредственно к выбранному провайдеру и конкретной модели.

### Маршрутизатор/агрегатор

Пример:

`project gateway/client → OpenRouter API → pinned model → upstream provider endpoint`

Здесь появляется дополнительный слой `OpenRouter`, а за ним — фактический поставщик модели.

Следовательно, нужно отдельно доказать:
- куда именно ушёл запрос;
- что провайдер действительно зафиксирован;
- что fallback отключён;
- что маршрут не переключится молча на другой upstream;
- что политика хранения/обработки доказана не только для `OpenRouter`, но и для фактического upstream-провайдера.

Маршрутизатор удобнее для переключения моделей, но сложнее для доказуемости маршрута.

## Почему Anthropic и Google допущены, а OpenRouter пока условный

КАНЦЕЛЯР проверил свежие официальные сведения для трёх вариантов.

### Anthropic

Прямой коммерческий/API-маршрут классифицирован:

- `ELIGIBLE_D0`;
- `ELIGIBLE_D1`.

Для первого маршрута предусмотрены ограничения:
- прямой `api.anthropic.com`;
- коммерческий/API-аккаунт, не потребительский Claude;
- точный `Claude model ID`;
- без Files API;
- без серверных инструментов, поиска и выполнения кода;
- без отправки обратной связи;
- без данных выше разрешённого класса.

### Google

Прямой управляемый маршрут Google к Gemini также классифицирован:

- `ELIGIBLE_D0`;
- `ELIGIBLE_D1`.

Условия включают:
- управляемый маршрут Google Cloud, не потребительский Gemini;
- точный `Gemini model ID`;
- явный региональный или юрисдикционный endpoint;
- журналирование запросов/ответов выключено;
- поиск/grounding выключен;
- сохранение взаимодействий выключено;
- восстановление сессий выключено;
- внешние инструменты выключены.

### OpenRouter

Для синтетического D0 маршрут возможен только при жёсткой фиксации:
- одной модели;
- одного upstream endpoint;
- `allow_fallbacks=false`;
- без model fallback;
- `data_collection=deny`;
- предпочтительно `zdr=true`;
- с `router_metadata=on`;
- без инструментов, файлов и кеша.

Но для D1 остаётся статус:

`CONDITIONAL`

Причина: собственных заявлений `OpenRouter` недостаточно. Для D1 нужна отдельная официальная доказательная база по фактическому upstream-провайдеру и проверка, что маршрут не может незаметно уйти к другому поставщику.

Поэтому Anthropic и Google являются **допущенными кандидатами по имеющимся доказательствам**, а не выбранными победителями. `OpenRouter` пока имеет более сложную цепочку доказательств.

## Что именно будет первым реальным пилотом

Первый внешний пилот должен быть максимально узким:

- только `D0_SYNTHETIC`;
- один прямой провайдер;
- одна точная модель;
- один точный API/endpoint;
- без fallback;
- без инструментов;
- без поиска;
- без подключаемых сервисов;
- без файлов;
- без рабочих данных проекта.

Задача первого пилота: доказать, что gateway может сделать контролируемый внешний вызов по заранее известному маршруту и сохранить точное происхождение результата.

Он не проверяет ещё всю будущую много-модельную систему сразу.

## Что запрещено передавать в первый пилот

Запрещены:
- любые реальные рабочие материалы проекта;
- приватные документы;
- персональные данные;
- секреты, токены, ключи, пароли;
- данные классов D2 и выше;
- содержимое подключённых сервисов;
- материалы из файлов проекта;
- любые данные, для которых ещё не утверждён внешний маршрут.

Также не разрешены инструменты, поиск, connectors и автоматический fallback.

## Что требуется решить ОПЕРАТОРУ

После чтения требуется выбрать **ровно один** вариант:

- `AUTHORIZE_ANTHROPIC_D0_PILOT`
- `AUTHORIZE_GOOGLE_D0_PILOT`
- `HOLD_EXTERNAL_PROVIDER_PILOT`

Это не выбор «лучшей модели вообще».

Это разрешение или запрет **одного первого синтетического внешнего маршрута**.

`OpenRouter` как первый реальный маршрут КООРДИНАТОРОМ сейчас не предлагается.

## Что разрешит такое решение

Если ОПЕРАТОР выберет Anthropic или Google, разрешается только подготовить/подключить exact D0 pilot path для выбранного прямого провайдера в уже заданных границах.

Это решение само по себе не разрешает:
- D1;
- D2 и выше;
- производственное использование;
- передачу данных проекта;
- произвольные подключаемые сервисы;
- поиск;
- инструменты;
- fallback;
- автоматическое принятие ответа модели;
- покупку/подписку сверх отдельно подтверждённого действия;
- выбор провайдера как постоянного архитектурного стандарта проекта.

## Что может быть дальше

После успешного D0 можно отдельно рассматривать следующие этапы, каждый с собственным решением и доказательной базой:

1. повторяемость и readback внешнего маршрута;
2. внешний режим АВТОР + независимый ПРОВЕРЯЮЩИЙ;
3. ограниченный класс D1 при сохранении разрешённых условий;
4. сравнение нескольких прямых провайдеров;
5. контролируемый `OpenRouter` D0 с жёстко зафиксированным upstream;
6. только после отдельных проверок — обсуждение более чувствительных классов данных.

Пока запрещено считать любой из этих этапов автоматически разрешённым вслед за D0.

## Текущая развилка

По имеющейся доказательной базе:
- Anthropic direct: кандидат для D0/D1;
- Google direct: кандидат для D0/D1;
- `OpenRouter`: D0 возможен при строгих ограничениях, D1 остаётся условным.

КАНЦЕЛЯР не выбирал провайдера за ОПЕРАТОРА. Этот текст тоже не выбирает.

Требуемое человеческое решение остаётся тем же:

`AUTHORIZE_ANTHROPIC_D0_PILOT`
или
`AUTHORIZE_GOOGLE_D0_PILOT`
или
`HOLD_EXTERNAL_PROVIDER_PILOT`.
