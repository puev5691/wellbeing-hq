## Основание

ОПЕРАТОР явно поручил внести необходимые дополнения в действующие нормы, правила, инструкции и источники после обнаруженного дефекта:
1. human-facing terminal result был выдан без ясного следующего шага ОПЕРАТОРА;
2. при approval-gate ОПЕРАТОР был отправлен по другим Сущностям за основаниями, которые уже существовали в информационном поле.

RED проверил действующие approved sources и установил:
- file-work canon уже требует не перекладывать на ОПЕРАТОРА догадки и давать короткую конкретную инструкцию;
- project core не содержит достаточно явной нормы human-facing terminal result + next Operator action;
- task-conveyor canon останавливает процесс на approval-gate, но не требует от KOO готового decision packet;
- entity roles требуют эскалацию ОПЕРАТОРУ, но не фиксируют запрет заставлять его собирать уже существующий evidence.

Минимальная корректная дельта поэтому затрагивает три источника.

## 1. project-instructions-core — добавить новый раздел

Нормативное место:
сразу после раздела `## Минимальный документооборот` и перед `## Доставка артефактов`.

### Человекочитаемые результаты и следующий шаг ОПЕРАТОРА

Если результат предназначен ОПЕРАТОРУ или иному человеку, сначала кратко и понятным русским языком указывается:

`что произошло → что это означает → что теперь возможно, разрешено, запрещено или требуется`.

После этого, если они нужны для проверки или исполнения, приводятся точные технические данные: machine status, version, commit/blob/tree, locator, path, protocol fields и другие literal identifiers.

Техническая точность имеет приоритет над литературностью. Source code, commands, config, logs, protocol literals, identifiers и machine-readable fields сохраняются буквально там, где изменение формы может снизить корректность.

Если после terminal result требуется решение, подтверждение или ручное действие ОПЕРАТОРА, human-facing результат обязан прямо указать **один конкретный следующий шаг ОПЕРАТОРА** и дать достаточно уже доступного основания, чтобы ОПЕРАТОР не реконструировал задачу по GitHub, очереди, locator или другим Entity-чатам. Если действие ОПЕРАТОРА не требуется, это следует сказать прямо.

Это правило не требует дополнительных документов, summary-файлов, cover notes или отдельных «человекочитаемых версий». Если один artifact может одновременно содержать понятное объяснение и точные machine fields, используется один artifact.

Pure machine-consumed code, config, logs и protocol data не требуют дополнительного русского пояснения.

Один machine status без человеческого объяснения недостаточен как результат, адресованный ОПЕРАТОРУ или иному человеку.

## 2. task-conveyor-canon — дополнить approval gate

Нормативное место:
сразу после абзаца:

`Если для следующего шага требуется новое approval/instruction, конвейер останавливается на соответствующем gate...`

Добавить:

Если gate требует решения ОПЕРАТОРА, КООРДИНАТОР не отправляет ОПЕРАТОРА собирать уже существующие основания по другим Сущностям. КООРДИНАТОР сам выполняет fresh reconciliation доступного evidence и формирует готовый **decision packet**, в котором кратко указаны:

- какое именно решение требуется от ОПЕРАТОРА;
- что уже проверено и что это означает;
- exact locator + immutable identity достаточных оснований;
- допустимые варианты решения, если их больше одного;
- последствия каждого варианта, если они существенны;
- один конкретный следующий шаг ОПЕРАТОРА.

Если обязательного основания действительно не хватает, КООРДИНАТОР сначала маршрутизирует недостающую профильную работу сам. ОПЕРАТОР привлекается к поиску/переносу основания только при проверяемой невозможности получить его доступными средствами или когда именно человеческое действие является содержанием gate.

### Дополнение роли ОПЕРАТОРА в task-conveyor

После строки:

`- не обязан самостоятельно реконструировать задачу из GitHub, очереди или набора locator;`

добавить:

`- если требуется его approval/decision, получает от КООРДИНАТОРА готовый decision packet, а не маршрут по другим Entity-чатам за уже существующими основаниями;`

### Дополнение роли KOO в task-conveyor

Перед текущим шагом «после нового результата снова читает информационное поле...» добавить:

`если следующий gate требует решения ОПЕРАТОРА, собирает уже существующие основания и формирует готовый decision packet;`

### Дополнение роли адресной Сущности в task-conveyor

После формирования terminal result добавить:

`если результат адресован человеку, сначала сообщает человеческий смысл результата; если требуется решение или действие ОПЕРАТОРА, прямо указывает один конкретный следующий шаг и достаточное основание;`

## 5. Каноническое действие для KAN/KOO

ОПЕРАТОР уже разрешил содержание поправок. Следующий нормативный контур должен без повторного хождения ОПЕРАТОРА по Сущностям:

1. проверить эту exact delta на отсутствие конфликта с текущими approved sources;
2. материализовать новые версии трёх источников;
3. зафиксировать explicit OPERATOR decision как authority basis из текущего поручения;
4. выполнить требуемую source-set publication / activation barrier / readback;
5. обновить active source identities;
6. вернуть ОПЕРАТОРУ один human-readable terminal result:
   - что изменено;
   - что это означает;
   - действует ли новая норма;
   - требуется ли ещё какое-либо действие ОПЕРАТОРА.

Если canonical activation требует отдельного формального подтверждения несмотря на уже данное поручение, KOO обязан вернуть один готовый decision packet с exact вариантами, а не отправлять ОПЕРАТОРА повторно в KAN/RED.
