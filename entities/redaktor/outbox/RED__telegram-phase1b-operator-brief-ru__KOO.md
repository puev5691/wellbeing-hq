# Telegram Phase 1B — операторская версия

Статус: `BLOCKED_WAITING_OPERATOR_AUTHORIZED_EXECUTION_DECISION`

## Что уже проверено

СИСАДМИН заново проверил выбранный непроизводственный сервер `ruvds-xnqc6`.

Подтверждено:
- это именно `ruvds-xnqc6`;
- текущий пользователь `pev5691`, uid/gid 1000, входит в группу `sudo`;
- будущий пользователь и группа `wellbeing-tg-p1b` пока не существуют;
- каталоги `/opt/wellbeing/telegram-phase1b-runtime-r01`, `/etc/wellbeing/telegram-phase1b`, `/var/lib/wellbeing/telegram-phase1b-sandbox` отсутствуют;
- unit `/etc/systemd/system/wellbeing-telegram-phase1b-sandbox.service` отсутствует;
- порт 8782 свободен;
- конфликтов имён пользователя, каталогов, unit и порта не найдено;
- `MAZHOR` не использовался и остаётся исключённым;
- производственная среда не менялась;
- реальный Telegram-вызов, токены, секреты, внешний webhook и reverse proxy не создавались.

То есть место для ограниченного непроизводственного запуска подготовлено логически: явных конфликтов нет.

## Что заблокировано

Заблокирован не сам сервер и не кандидат программы.

Заблокирован **доказанный путь выполнения команд с повышенными правами** на `ruvds-xnqc6`.

Проверочная команда содержала:

`sudo -n true`

Текущий разрешённый удалённый интерфейс не выполнил её и вернул:

`Command not allowed`

Поэтому СИСАДМИН не имеет права утверждать, что через имеющийся удалённый канал он действительно может выполнить требуемое привилегированное создание пользователя, каталогов, unit и последующую проверку результата.

Из-за этого изменения на сервере намеренно не начинались.

## Почему членство в группе `sudo` ничего не доказывает

Факт, что `pev5691` входит в группу `sudo`, говорит только о системной принадлежности пользователя к этой группе.

Он **не доказывает**, что конкретный разрешённый нам механизм удалённого выполнения:
- пропустит команду `sudo`;
- сможет выполнить её без интерактивного ввода;
- имеет разрешение на требуемые root-операции;
- позволит затем проверить созданное состояние.

Иными словами:

**пользователь может иметь право на `sudo`, а наш текущий исполнитель команд может не иметь права этим воспользоваться.**

Именно это сейчас и наблюдается.

## Какое решение требуется от ОПЕРАТОРА

Нужно выбрать один из двух вариантов:

1. разрешить/предоставить на `ruvds-xnqc6` такой путь выполнения, через который СИСАДМИН сможет выполнить уже заданное ограниченное непроизводственное привилегированное развёртывание и последующую проверку;

или

2. явно указать уже одобренный механизм, через который СИСАДМИН должен выполнить эти действия на том же `ruvds-xnqc6`.

Пароли, токены, приватные ключи и другие секреты в GitHub передавать не требуется и нельзя.

## Что это решение НЕ разрешает

Даже после решения вопроса с повышенными правами автоматически не разрешаются:
- другой сервер;
- `MAZHOR`;
- производственное развёртывание;
- реальная отправка сообщений в Telegram;
- публичный webhook;
- публикация секретов;
- изменение reverse proxy;
- расширение полномочий или прав записи;
- переход к любым работам вне уже выданной непроизводственной задачи Phase 1B.

## Что СИСАДМИН делает после решения

После получения допустимого пути СИСАДМИН обязан работать по Resume-First:

1. заново проверить `ruvds-xnqc6` перед любыми изменениями;
2. убедиться, что состояние сервера не изменилось и по-прежнему нет конфликтов;
3. только затем выполнить ровно то ограниченное привилегированное развёртывание, которое уже разрешено задачей;
4. выполнить readback, то есть проверить фактически созданного пользователя, каталоги, unit, sandbox DB и связанные ограничения;
5. вернуть проверяемый результат КООРДИНАТОРУ.

До появления разрешённого привилегированного пути корректный статус остаётся:
