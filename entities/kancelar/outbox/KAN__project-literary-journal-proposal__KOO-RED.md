## Смысл

Проекту нужен отдельный человеческий слой памяти, пригодный РЕДАКТОРУ как исходный материал для Telegram, портала и будущей книги/истории проекта.

Это не технический лог, не полный transcript и не второй источник истины о текущем состоянии.

Журнал должен сохранять только те события и человеческие подробности, которые помогают понять, **как проект развивался, почему принимались решения и что в этом было человечески важного, характерного или смешного**.

## Что стоит сохранять

Только значимое, например:

- важное событие или достигнутый рубеж;
- решение, изменившее направление работы;
- поворотный момент;
- серьёзную неудачу и вывод из неё;
- открытие, неожиданное наблюдение или полезный эксперимент;
- причину важного выбора;
- человеческий контекст, без которого событие теряет смысл;
- характерный или смешной эпизод;
- короткую прямую реплику, если она действительно ценна;
- аккуратный пересказ диалога, если дословная цитата не нужна;
- последствия события для дальнейшей истории проекта.

Если используется дословная цитата, она должна быть именно цитатой из доступного источника. Пересказ не оформляется как дословная речь.

## Что не должно попадать в журнал автоматически

Не переносить туда только ради полноты:

- commits, blobs, hashes, paths, locators;
- route history;
- обычные machine statuses;
- сырые логи;
- полные technical reports;
- routine terminal results;
- полный transcript чатов;
- повторяющиеся операционные действия;
- машинную телеметрию без исторической или литературной ценности.

Если техническое evidence нужно для проверки истории, достаточно exact locator/immutable identity без копирования машинной шелухи в повествование.

## Лёгкая форма одной записи

Формат не должен быть жёсткой машинной схемой. Достаточно, чтобы из записи было понятно:

1. что случилось;
2. почему это было важно;
3. какой человеческий контекст или деталь стоит сохранить;
4. к чему это привело;
5. при необходимости — где лежит technical evidence.

Это ориентир для редакторской памяти, а не обязательный набор служебных полей.

## Периодичность

Не создавать новый journal artifact на каждую задачу и не требовать запись после каждого terminal result.

Предпочтительная модель:

- одна долговременная редакторская подборка или небольшой набор тематических/периодических частей;
- пополнение после действительно значимых эпизодов;
- периодическая редакторская сборка материала из уже существующих human-facing results и диалогов;
- отдельная фиксация только тогда, когда есть риск потерять ценную человеческую историю.

Точная календарная периодичность не устанавливается.

## Authority / truth boundary

Литературный журнал:

- не является authoritative current-state;
- не является recovery package;
- не подтверждает task status, delivery, receipt, acceptance или authority;
- не заменяет GitHub evidence и Project Sources;
- не используется для автоматического восстановления технического состояния;
- не становится public-ready только потому, что событие записано.

При публикации фрагмента применяются обычные редакторские, privacy, public и authority boundaries проекта.

## Минимальный будущий владелец

Рекомендуемый основной владелец: **RED / РЕДАКТОР** в рамках уже существующей роли «живой текст, читаемость, стиль, публикации».

Изменение `entity-roles-short` для этого не требуется: ведение редакторского источника укладывается в действующую роль RED.

Дополнительные функции без смены владельца:

- ARH при необходимости сохраняет значимые snapshots/provenance журнала как проектной памяти, но не становится автором повествования;
- KOO может маршрутизировать значимые события/материалы в RED, но не обязан быть редактором;
- KAN подключается только если конкретная запись затрагивает normative/public/privacy/commitment boundary.

## Минимальное будущее нормативное место

Не делать литературный журнал новым baseline Project Source.

Если ОПЕРАТОР позднее решит активировать журнал, достаточно **одной короткой профильной инструкции RED**, подключаемой только к редакторской работе, плюс самого долговременного journal artifact/набора частей.

То есть рекомендуемый нормативный дом:

`RED profile regulation / editorial working source`

а не project core, file-work canon, task-conveyor или recovery canon.

Exact path и storage layout следует выбрать только на отдельном activation/design шаге, чтобы эта proposal не превращалась в скрытое решение реализации.

## Public / privacy boundary

Журнал может хранить внутренний человеческий контекст, но это не означает разрешение публиковать его полностью.

Не включать без отдельного основания:
- секреты;
- чувствительные персональные данные;
- приватные данные третьих лиц;
- служебные детали, которые не разрешены для публичного распространения.

Подготовка материала к Telegram, порталу или книге является отдельной редакторской/publication задачей.

## Scope boundaries

Эта proposal:

- не создаёт новый обязательный journal artifact;
- не вводит per-task reporting;
- не меняет approved roles;
- не меняет Project Sources;
- не запускает journal automation;
- не объявляет журнал источником истины;
- не задаёт тяжёлую schema;
- не активирует журнал;
- не смешивается с immediate core-language amendment.

## RED review handoff

RED должен проверить:

- полезность материала для будущего Telegram/портала/книги;
- естественность предлагаемой формы;
- достаточно ли отделён человеческий слой от machine evidence;
- не превращается ли предложение в обязательную бюрократию;
- адекватен ли RED как минимальный будущий владелец без изменения roles.

RED не должен активировать журнал или проектировать automation.
