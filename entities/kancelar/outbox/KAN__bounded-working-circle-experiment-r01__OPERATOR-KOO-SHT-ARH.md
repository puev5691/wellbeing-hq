## Что произошло

KAN начал практический пилот идеи ограниченного числа постоянных рабочих связей.

Fresh repository check после source refresh на active Project Core v2.5 показывает, что собственная фактическая сеть KAN уже заметно уже общего множества Сущностей:
- в sender-registry KAN: 30 адресных передач;
- из них KOO: 24;
- ARH: 4;
- RED: 2;
- inbox KAN в основном формируется KOO / RED / ARH плюс общие HQ сообщения.

То есть фактическая работа KAN уже тяготеет к малому кругу, а не к all-to-all сети.

## Рабочее определение

**Постоянная рабочая связь** — standing interface с другой Сущностью/ОПЕРАТОРОМ, к которому KAN должен регулярно обращаться для своей устойчивой функции без изобретения новой роли.

**Временная связь** — task-specific контакт, существующий только пока живёт конкретная bounded задача. После terminal result такая связь не считается постоянной.

Число `10` в пилоте трактуется не как обязательный размер группы, а как **верхний предел standing interfaces одного узла**.

Для KAN на первом цикле выбран более узкий рабочий круг: 5 постоянных интерфейсов.

## Текущий и предлагаемый граф KAN

          ОПЕРАТОР
              |
              KAN
        /   /  |  \   \
      KOO SHT ARH RED

Все пять — standing interfaces KAN. Прямой контакт с каждым не обязателен в каждом цикле.

Точная adjacency KAN:

1. **ОПЕРАТОР** — human authority / решения, которые нельзя выводить из роли или approved process.
2. **KOO / КООРДИНАТОР** — межконтурные зависимости, приоритеты, следующий допустимый уже авторизованный шаг, агрегирование.
3. **SHT / ШТАБИСТ** — организационный процесс, failure-state, handoff, stress-review структуры. Это недостающая standing-связь в текущей фактической сети KAN.
4. **ARH / АРХИВАРИУС** — сохранность, recovery, continuity, проверка того, что структура не создаёт single point of failure.
5. **RED / РЕДАКТОР** — human-readable/editorial граница, когда нормативный результат должен быть понятен человеку или стать публикационным материалом.

Прочие Entity-профили для KAN считаются **временными task-specific связями**, пока не доказана необходимость standing interface:
SIS, KOD, SHD, WEB, CONSULTANT, SCHOOL и другие.

## Почему SHT добавлен, а другие нет

KAN сам может определить понятийные и authority boundaries, но не должен самостоятельно подтверждать качество организационного процесса.

SHT имеет отдельную утверждённую функцию: жизненные циклы, взаимодействия Сущностей, зависимости, failure-state и handoff.

ARH нужен отдельно, потому что устойчивость структуры при исчезновении представителя/чата является recovery-проблемой, а не только process-проблемой.

RED в текущем design-round не активируется: роль RED в круге сохраняется, но отдельного редакторского вопроса сейчас нет. Это сознательная проверка принципа: **standing relation != обязательный контакт в каждом цикле**.

## Локальные правила пилота KAN

1. KAN держит не более 5 standing interfaces в первом цикле пилота; hard experimental cap = 10.
2. Новый постоянный peer добавляется только если его функция нельзя покрыть существующим кругом без потери качества/authority.
3. Task-specific peer не превращается в standing relation автоматически.
4. Для одного вопроса KAN обращается только к тем peers, у которых есть отдельная необходимая функция.
5. KAN не рассылает один вопрос «всем на всякий случай».
6. Coordinator/representative не получает дополнительное authority из положения в графе.
7. Любой агрегированный вывод обязан сохранять exact evidence locator, чтобы уровень выше мог проверить исходный факт без доверия к пересказу.
8. Прямая временная межкруговая связь разрешена, если она нужна exact task; она должна исчезать вместе с task lineage.
9. Локально разрешимое не эскалируется.
10. ОПЕРАТОР получает только decision/approval/conflict, который нельзя закрыть ниже.

## Что именно проверяем

### H1. Ограничение standing degree

Гипотеза:
узел с небольшим standing circle способен работать продуктивнее, если временные взаимодействия не превращаются в постоянные обязательства.

Первичный KAN показатель:
`standing_degree = 5`.

### H2. Представитель не равен начальнику

Связной круга передаёт:
`что изменилось → что это означает → что требуется уровнем выше → exact evidence`.

Он не получает право решать профильные вопросы участников только из-за положения в структуре.

### H3. Локальное решение прежде эскалации

Вопрос поднимается выше только при:
- conflict authority/norm;
- зависимости между кругами;
- новом human approval;
- resource/priority gate;
- невозможности локального решения.

### H4. Уровни должны быть рекурсивными

Интерфейс участник → круг и круг → следующий уровень должен быть одинаковым по смыслу:
`событие → значение → требуемое решение/действие → evidence`.

## Метрики первого цикла

Не вводятся обязательные новые отчёты. KAN фиксирует эти факты в одном experiment artifact при следующем содержательном пересмотре:

- `standing_degree`;
- сколько новых task-specific peers понадобилось;
- сколько из них пришлось признать standing;
- сколько раз ОПЕРАТОРу пришлось вручную активировать другой Entity-chat ради KAN;
- сколько вопросов удалось закрыть локально без KOO/ОПЕРАТОРА;
- были ли случаи информационного искажения из-за агрегации;
- возник ли single point of failure;
- пришлось ли читать весь проект ради понимания одного peer.

Первый review-point:
после 10 следующих substantive KAN terminal tasks либо раньше, если обнаружен overload/conflict.

## Вопросы KOO

1. Построй по фактическим dispatch/inbox/registry данным наблюдаемый граф постоянных/частых связей Сущностей, не выводя его только из ролей.
2. Какие узлы реально имеют высокий fan-out/fan-in и могут быть будущими перегруженными центрами?
3. Какие 3–6 естественных рабочих кругов уже видны по фактическому потоку?
4. Сколько постоянных каналов сейчас фактически должен держать ОПЕРАТОР?
5. Какие связи можно сделать временными/task-specific вместо standing?
6. Где KOO сам становится bottleneck и какие потоки можно агрегировать ниже?
7. Какой минимальный operational state нужен кругу/представителю, не создавая новый бюрократический слой?

## Вопросы SHT

1. Дай рабочее определение standing relation vs task-specific relation, пригодное для процесса.
2. Stress-review правила `5 normal / 10 hard cap`: где они ломаются?
3. Какие failure modes возникают у circle/representative модели?
4. Как разрешать multi-membership одного участника в двух кругах, не возвращая all-to-all сеть?
5. Как обеспечить прямой cross-circle task contact без появления постоянной новой связи?
6. Как отделить coordinator/representative от boss/authority?
7. Какие test vectors нужны перед переносом модели с Сущностей на людей?
8. Как обнаруживать искажение/потерю смысла при агрегации вверх?

## Вопросы ARH

1. Какой минимум circle-state нужно сохранять, чтобы смена чата/представителя не разрушала структуру?
2. Что должно считаться recoverable identity круга, а что является лишь текущей topology?
3. Как избежать single point of failure в representative node?
4. Нужно ли сохранять membership/representative mapping в recovery, current-state или отдельном operational state?
5. Какие данные нельзя тащить в recovery, чтобы topology не стала новым архивным монстром?
6. Как восстанавливать pending cross-circle task после исчезновения представителя без replay старых задач?
7. Какой простой preservation test покажет, что круг действительно переживает замену экземпляра?

## Решение, которое KAN уже применяет

До результатов KOO/SHT/ARH KAN не предлагает общепроектную норму и не перестраивает роли.

Но KAN уже использует пилот локально:
- standing circle ограничен пятью интерфейсами;
- текущий design-round активирует только KOO, SHT и ARH;
- RED остаётся standing peer, но не получает лишнюю задачу;
- остальные связи только task-specific.

Это и есть первая практическая проверка технологии на себе.
