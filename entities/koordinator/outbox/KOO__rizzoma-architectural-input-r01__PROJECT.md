## Source

Operator-provided research handoff:
`RIZZOMA__research-handoff__KOO.md`

Core conclusion accepted as architectural input:
Rizzoma is useful primarily as a source of ideas for turning conversation into a structured collaborative information field, not as a technology stack to fork or deploy.

## Preserved architectural ideas

1. conversation-as-document;
2. tree-structured semantic discussion;
3. contextual task/result near the reason it emerged;
4. addressable semantic nodes / mentions;
5. causal history / playback;
6. progressive structuring;
7. mandatory export from live workspace into independent verifiable artifacts.

## Project fit

Potentially complementary layers:

Machine/project discipline:
`source → task → Entity → artifact → check → routing → receipt → recovery`

Human interaction layer:
`discussion → structure → action → result → knowledge`

Any future interface must preserve:
- meaningful results as standalone artifacts;
- UI does not define authoritative/current;
- capability does not create authority;
- mention does not equal delivery;
- version identity remains verifiable;
- receipt does not equal acceptance;
- recovery does not depend on chat memory;
- provenance and causal history remain preserved.

## Current project application points

### Public information portal / information field
Use as design input for future navigation and causal-history views:
- topic/context as a working semantic context;
- branch/node as a semantic discussion node;
- task-in-context as visible causal linkage;
- history playback as human-readable explanation of how a state emerged;
- export as first-class path from live UI to versioned artifact.

### Telegram facilitator
Use as design input for:
- tree/branch representation of discussion;
- semantic nodes around problem/goal/claim/question/task/result;
- contextual candidate_task creation;
- addressable mentions as UI hints only, never authority/delivery;
- progressive structuring from natural discussion into explicit semantic state.

### Entity routing / orchestration
Potential future fit-gap:
`wave → blip → branch → mention → task → history → export`
vs
`source → task → Entity → artifact → check → routing → receipt → recovery`.

## Explicit non-actions

Do not:
- deploy/fork Rizzoma;
- replace GitHub;
- change routing/recovery canon;
- create a new Entity;
- assign immediate implementation of a Rizzoma clone;
- treat mention as delivery/authority;
- treat live UI as authoritative source.

## Trigger for future dedicated fit-gap

Only when one of these becomes active:
- unified information-field UI design;
- reducing manual transfer from discussion to artifacts;
- semantic Entity routing;
- causal history UI;
- shared human+AI workspace.

Then issue a bounded modern fit-gap task instead of a porting task.
