# Краткоживущие исполнители — проект упрощения R01

Статус — CANDIDATE / NOT_ACTIVE. Подтверждённое ОПЕРАТОРОМ направление разрешает подготовку этого проекта. Оно не утверждает текст, не включает автоматику и не изменяет действующие источники или статус SIS.

## 1. Что меняется

Отдельная задача больше не требует продолжения старого чата. Новый исполнитель получает проверенные входы, выполняет одну задачу, оставляет результат во внешнем поле и завершает работу. Роль и рабочее состояние сохраняются вне чата. Продолжение задачи определяется записью в проекте, а не памятью экземпляра.

Проблема SIS r0.9 показала разницу между подтверждённым выполнением инициации и доказательством, что сегодняшний диалог — тот самый экземпляр. Второй вопрос нужен только там, где действие действительно зависит от прав или несохранённого состояния прежнего экземпляра. Требование специальной технической аттестации всех чатов не вводится.

## 2. Два режима работы

| Режим | Вход | Допустимый выход |
| --- | --- | --- |
| Временный исполнитель | Точное поручение и проверяемый контекст задачи | Отдельный кандидат-результат или точный blocker. Без права менять authoritative current-state |
| Держатель текущего состояния | Установленное полномочие на запись, актуальная версия состояния и точное основание операции | Принятие результата или ограниченное изменение состояния с проверкой версии и отсутствия конфликтующей записи |

Временный исполнитель не получает Writer Gate и не нуждается в self-snapshot после завершения каждой задачи. Если важное состояние возникло в ходе работы, оно сохраняется в результате или проверяемой контрольной точке до закрытия попытки. Для держателя состояния сохраняются правила recovery и передачи writer. Продолжение того же writer не означает повторный Writer Gate на каждую задачу. Смена writer требует отдельного действующего основания.

## 3. Один запуск, один результат

Минимальная запись задачи содержит ID задачи и попытки, роль исполнителя, результат и критерий приёмки, область допустимых действий, основание полномочия и неизменяемые ссылки на обязательные входы. Для постановщика достаточно короткого описания результата. Версии роли и базовых источников подставляет механизм запуска из действующего набора, а не человек вручную.

1. Запуск свежего исполнителя. Механизм загружает действующий минимум правил и точные входы. Перед работой подтверждает актуальность задачи и полномочие, проверяет отсутствие завершённого результата и резервирует одну исполнимую попытку. Доставка поручения не считается началом исполнения.
2. Исполнение и проверка. Исполнитель работает в указанной области. Отсутствие существенного входа или полномочия останавливает только эту задачу. Неизвестное состояние не восстанавливается догадкой.
3. Фиксация. Один результат по точному ID попытки содержит итог, значимые входы, доказательство результата и следующий шаг, если он нужен. Попытка закрывается только после проверки сохранённой версии. Содержательную приёмку фиксируют отдельно, когда от неё зависит решение или следующий допуск. Достаточно полей одной проверяемой записи, отдельный файл для каждого события не нужен.

Повторная доставка не запускает завершённую попытку. При сбое между сохранением и закрытием механизм сначала ищет и проверяет уже записанный результат. Если нельзя установить исход предыдущего действия, повтор не происходит автоматически. Для прерванной работы новую попытку разрешает применимое правило с явной связью с предыдущей.

Для принятия результата в authoritative current-state назначенный writer проверяет полномочие и ожидаемую версию. Переход происходит только при совпадении версии и отсутствии конфликта. Публикация кандидата не означает принятия. Автоматика может применять заранее утверждённые правила, но не может сама выдать разрешение на запуск, запись или производственное действие. Ручное решение нужно только там, где его нельзя заменить действующим правилом или где есть конфликт, неопределённый исход либо выход за разрешённый объём.

## 4. Точечные изменения в нормах

- **Recovery Canon v1.6, «Wake → Resume / Initiation → Writer Gate → Exact Task» и «Несколько экземпляров и current-writer».** Выделить запуск нового временного исполнителя из проверенного контекста как отдельный путь без проверки связи со старым чатом и без полномочия writer. Сохранить Resume-First для действительно продолжаемого экземпляра, а recovery, проверку writer и защиту от конкурентной записи — для операций, которые от них зависят. Не требовать полного recovery-пакета чужого экземпляра, если задача не зависит от его состояния.
- **Task Conveyor v1.2, разделы 1, 7–10.** Сохранить ручную передачу для действующих чатов. Добавить запуск нового исполнителя по текущей записи задачи. Транспорт не создаёт полномочий. Убрать обязательный перенос отдельного PROMPT там, где исполнитель получает те же данные из информационного поля. Сохранить проверяемую связь между задачей, попыткой и результатом.
- **Core v2.5 и Source Loading v2.2.** Согласовать границу между полным recovery держателя состояния и минимальным проверенным контекстом временного исполнителя. Файловый канон и распределение ролей не переписывать. АРХИВАРИУС сохраняет ответственность за recovery, но не участвует в каждом штатном запуске.

## 5. Один сквозной пилот после утверждения объёма

Дать первому новому исполнителю без доступа к старым чатам синтетический список документов и поручить подготовить индекс по заданному правилу. Второй новый исполнитель получает точную ссылку на сохранённый индекс, проверяет его и составляет следующий полезный артефакт — список отсутствующих ссылок. Оба запуска используют только тестовые документы и отдельную область результатов.

Пилот успешен, если оба результата проверяемы, второй экземпляр не читает чаты и не повторяет первую работу, ОПЕРАТОР не переносит контекст вручную, а повторная доставка первой задачи не создаёт дубль. Дополнительно подать устаревшую версию входа и убедиться, что действие не началось. Измерить число ручных действий, промежуточных файлов и повторных запусков. Пилот не меняет канон, не проверяет производственную готовность и не включает SECE.

## 6. Получение ответа АРХИВАРИУСА и граница SIS r0.9

Ответ ARH по предыдущему поручению получен по ссылке ОПЕРАТОРА, прочитан в точной версии и принят в учёт как документальное подтверждение. ARH подтвердил получение результата KOO и содержательно принял его с ограничением: техническая непрерывность SIS r0.9 не подтверждена. Это закрывает адресную передачу KOO → ARH, но не подтверждает continuity. Существующая запись writer SIS r0.9 не меняется. Основания объявить чат утраченным не установлено. Инициация r1.0, freeze, новый Writer Gate, повтор прежних задач и изменение recovery не выполнялись.
