# Универсальный канон работы с файлами для Сущностей и проектов

Кратко:
этот документ задаёт общий порядок работы с файлами, отчётами, скриптами, маршрутами и техническими пакетами для всех Сущностей и всех проектов, где ОПЕРАТОР использует file-first / shell-first рабочий цикл.

Главный принцип:
значимый результат должен существовать как самостоятельный файл или пакет файлов. Чат нужен для краткого смысла, указания места запуска, маршрута передачи и фиксации проблемы, а не для переноса длинных документов, скриптов и отчётов простынями текста.

## 0. Статус этой редакции

Статус этого файла:

    candidate_for_operator_approval

Назначение:

    candidate-редакция для замены `file-work-canon-universal-v2_3-approved.md` после решения ОПЕРАТОРА.

Эта редакция сохраняет правило минимального документооборота и модель межсущностной доставки артефактов: физическая передача файла либо проверяемая locator-based delivery существующего артефакта.

Активация отдельного Entity-чата и передача управления по task conveyor вынесены в отдельный канон и этим документом не регулируются.

Этот документ заменяет разрозненные частные каноны работы с файлами там, где они слабее или создают путаницу.

Если профильный канон Сущности строже этого документа, применяется более строгий профильный канон.

Если профильный канон требует больше документов без прямой пользы для выполнения задачи, применяется этот универсальный канон и правило минимального документооборота.

## 1. Назначение документа

Этот канон нужен, чтобы каждая Сущность:

- не выдумывала наличие файлов, путей, результатов команд и состояния систем;
- не превращала чат в склад длинных скриптов;
- не требовала от ОПЕРАТОРА угадывать, где запускать команду и какой отчёт вернуть;
- создавала проверяемые файлы и отчёты, а `route-note` и `manifest` — только когда они нужны маршруту или пакету;
- различала подготовительный шаг, реальное исполнение и фиксацию результата;
- передавала значимые материалы адресным Сущностям через понятный маршрут;
- не считала локальное копирование или простую публикацию завершением адресного маршрута без предусмотренного delivery/receipt.

Документ применим к техническим, организационным, редакционным, исследовательским, канцелярским, инфраструктурным и обучающим задачам.

## 3. Главный принцип file-first

В рабочих задачах результатом должен быть:

- файл;
- пакет файлов;
- архив;
- скрипт;
- отчёт;
- маршрутная записка;
- manifest;
- запрос недостающих данных.

Чат используется только для:

- краткого смысла;
- ссылки или пути к созданному файлу;
- указания, где запускать;
- указания, что загрузить обратно;
- фиксации стоп-условия;
- короткого вопроса на уточнение;
- аварийной команды, если файл создавать дольше и опаснее.

Нельзя считать значимый рабочий результат выполненным, если он существует только в длинном сообщении чата и не оформлен файлом.

## 4. Базовая формула file-first цикла

Правильный цикл внутри одной исполнительной среды:

    задача
    -> проверка исходных данных
    -> файл или пакет
    -> исполнение
    -> проверяемый результат / отчёт
    -> анализ

Если следующий шаг должен выполнить другой Entity-чат, дальнейшая передача управления выполняется по task-conveyor canon. Этот файловый канон не дублирует алгоритм межчатовой активации.
