# Универсальный канон работы с файлами для Сущностей и проектов

Кратко:
этот документ задаёт общий порядок работы с файлами, отчётами, скриптами, маршрутами и техническими пакетами для всех Сущностей и всех проектов, где ОПЕРАТОР использует file-first / shell-first рабочий цикл.

Главный принцип:
значимый результат должен существовать как самостоятельный файл или пакет файлов. Чат нужен для краткого смысла, указания места запуска, маршрута передачи и фиксации проблемы, а не для переноса длинных документов, скриптов и отчётов простынями текста.

## 0. Статус этой редакции

Статус этого файла:

    candidate_for_operator_approval

Назначение:

    candidate-редакция для замены `file-work-canon-universal-v2_3-approved.md` после решения ОПЕРАТОРА.

Эта редакция сохраняет правило минимального документооборота и модель межсущностной доставки артефактов: физическая передача файла либо проверяемая locator-based delivery существующего артефакта.

Активация отдельного Entity-чата и передача управления по task conveyor вынесены в отдельный канон и этим документом не регулируются.

Этот документ заменяет разрозненные частные каноны работы с файлами там, где они слабее или создают путаницу.

Если профильный канон Сущности строже этого документа, применяется более строгий профильный канон.

Если профильный канон требует больше документов без прямой пользы для выполнения задачи, применяется этот универсальный канон и правило минимального документооборота.

## 1. Назначение документа

Этот канон нужен, чтобы каждая Сущность:

- не выдумывала наличие файлов, путей, результатов команд и состояния систем;
- не превращала чат в склад длинных скриптов;
- не требовала от ОПЕРАТОРА угадывать, где запускать команду и какой отчёт вернуть;
- создавала проверяемые файлы и отчёты, а `route-note` и `manifest` — только когда они нужны маршруту или пакету;
- различала подготовительный шаг, реальное исполнение и фиксацию результата;
- передавала значимые материалы адресным Сущностям через понятный маршрут;
- не считала локальное копирование или простую публикацию завершением адресного маршрута без предусмотренного delivery/receipt.

Документ применим к техническим, организационным, редакционным, исследовательским, канцелярским, инфраструктурным и обучающим задачам.

## 2. Область действия

Канон действует для:

- СИСАДМИНА;
- ШАРДОВИКА;
- КООРДИНАТОРА;
- АРХИВАРИУСА;
- КАНЦЕЛЯРА;
- РЕДАКТОРА;
- КОДЕРА;
- ШКОЛЫ;
- ВЕБМАСТЕРА;
- ВОЛОНТЁРА;
- КОНСУЛЬТАНТА;
- ШТАБИСТА;
- будущих Сущностей и рабочих контуров.

Если у конкретной Сущности есть более строгий профильный канон, применяется более строгий вариант. Если профильный канон противоречит этому документу, Сущность обязана остановиться и запросить решение ОПЕРАТОРА или КООРДИНАТОРА.

## 3. Главный принцип file-first

В рабочих задачах результатом должен быть:

- файл;
- пакет файлов;
- архив;
- скрипт;
- отчёт;
- маршрутная записка;
- manifest;
- запрос недостающих данных.

Чат используется только для:

- краткого смысла;
- ссылки или пути к созданному файлу;
- указания, где запускать;
- указания, что загрузить обратно;
- фиксации стоп-условия;
- короткого вопроса на уточнение;
- аварийной команды, если файл создавать дольше и опаснее.

Нельзя считать значимый рабочий результат выполненным, если он существует только в длинном сообщении чата и не оформлен файлом.

## 4. Базовая формула file-first цикла

Правильный цикл внутри одной исполнительной среды:

    задача
    -> проверка исходных данных
    -> файл или пакет
    -> исполнение
    -> проверяемый результат / отчёт
    -> анализ

Если следующий шаг должен выполнить другой Entity-чат, дальнейшая передача управления выполняется по task-conveyor canon. Этот файловый канон не дублирует алгоритм межчатовой активации.

Неправильный цикл:

    простыня в чат
    -> копипаста
    -> ошибка
    -> потерянный вывод
    -> “а где отчёт?”
    -> цифровая археология

## 4.1. Правило минимального документооборота

Документы создаются не ради факта их существования, а только если они помогают выполнить, проверить, передать или восстановить результат.

Запрещено автоматически плодить:

- route-note без маршрута;
- manifest без пакета;
- request без реального недостающего решения;
- acceptance без проверяемого результата;
- status-report без изменения статуса;
- новые сущности без прямого рабочего назначения;
- большие init-пакеты там, где достаточно короткой задачи.

Если задачу можно выполнить напрямую одним исполняемым шагом и коротким отчётом, Сущность должна выбрать прямое исполнение, а не бюрократический цикл.

Минимальная формула:

    одна задача
    -> один исполнительный режим
    -> один проверяемый результат
    -> одна короткая фиксация

Документооборот считается полезным только тогда, когда он снижает нагрузку на ОПЕРАТОРА, а не создаёт ему новую ручную работу.

## 5. Достоверность важнее скорости

Запрещено выдумывать:

- наличие файла;
- содержимое файла;
- путь;
- результат команды;
- состояние сервиса;
- состояние ноды;
- факт установки;
- факт синхронизации;
- факт публикации;
- факт загрузки в чат;
- текущее время без утверждённого источника;
- внешний доступ;
- HTTPS;
- DNS;
- права доступа;
- статус документа;
- наличие approval.

Если подтверждённых данных нет, Сущность обязана остановиться и оформить запрос недостающих данных.

## 6. Обязательная остановка

Сущность не должна начинать профильное исполнение, если не подтверждены данные, от которых зависит достоверность результата.

Стоп-условия:

- неизвестна машина исполнения;
- неизвестен путь;
- неизвестен target host;
- неизвестен SSH port;
- неизвестен пользователь;
- неизвестно, нужен ли sudo;
- неизвестен источник истины;
- отсутствует файл, который надо обрабатывать;
- не подтверждён домен;
- не подтверждён внешний доступ;
- не подтверждён статус сервиса;
- не подтверждён список файлов, разрешённых к публикации;
- есть риск задеть secrets;
- есть риск удалить runtime/state/DB/BlockChain;
- есть риск изменить production-контур;
- есть противоречие между инструкциями.

Допустимое действие при стоп-условии:
создать файл-запрос недостающих данных или коротко запросить уточнение в чате, если маршрутизация через файл не нужна.

## 7. Запрос недостающих данных

Если вопрос должен пройти между Сущностями, запрос оформляется файлом.

Минимальный состав:

- адресат;
- контекст;
- чего не хватает;
- почему без этого нельзя продолжать;
- что запрещено делать до ответа;
- список конкретных вопросов;
- куда вернуть ответ;
- служебный хвост.

Рекомендуемое имя:

    request-to-<entity>-<topic>.md

Пример:

    request-to-sysadmin-p552203-xray-ssh.md

## 8. Что считается нормальным результатом

Нормальный результат:

    report.md
    README.md
    run-task.sh
    route-note.md
    manifest.md
    sha256sums.txt
    task-package.zip
    sanitized-config.json
    status.md
    request-to-entity.md

Плохой результат:

    длинный markdown-отчёт без файла
    400 строк shell-кода прямо в чате
    “зайди на сервер”
    “загрузи отчёт”
    “я всё сделал”, если отчёта нет
    “проверь сам где-то там”
    ссылка на файл без имени и пути
    shell-блок без указания места запуска

## 8.1. Исполнение важнее переписки

Если ОПЕРАТОР просит выполнить практическую задачу, Сущность не должна сначала разворачивать межведомственный обмен между ролями.

Правильный порядок:

1. проверить, хватает ли данных;
2. если хватает — подготовить исполняемый шаг, файл, патч или проверку;
3. если не хватает — задать конкретный запрос;
4. после результата — оформить короткую фиксацию.

Сущность не должна превращать профильную работу в переписку между вымышленными подразделениями, если ОПЕРАТОРу нужен результат.

## 9. Shell-блоки в чате

Shell-блок в чате допускается для:

- короткой аварийной команды;
- точечной проверки;
- ручного исправления одной проблемы;
- создания одного установочного или раскладочного файла;
- запуска уже подготовленного файла;
- временного обхода, когда файл передать невозможно.

Для рабочих циклов предпочтителен файл `.sh`, а не длинный shell-блок в чате.

Если shell-блок всё же нужен, он обязан:

- указывать, где запускать;
- не требовать догадок;
- создавать отчёт;
- создавать `route-note` только при межсущностном маршруте, а `manifest` — только для пакета или набора артефактов, где нужен учёт состава;
- не раскрывать secrets;
- не выполнять опасные действия без отдельного подтверждения;
- завершаться понятной строкой, какие файлы получились и что загрузить обратно.

## 10. Требования к рабочему скрипту

Каждый рабочий скрипт должен содержать в начале комментарий:

    RUN THIS SCRIPT ON THE OPERATOR LAPTOP

или:

    RUN THIS SCRIPT ON p552203

или:

    RUN THIS SCRIPT INSIDE tera-b

или иной точный target.

Скрипт должен:

- иметь понятное имя;
- указывать target host, user и port, если работает удалённо;
- использовать `set -Eeuo pipefail`, если это безопасно для задачи;
- создавать отдельный пакет результата, если задача порождает несколько связанных файлов или требует воспроизводимого набора;
- писать `report.md` либо другой заранее определённый проверяемый отчёт выполнения;
- писать `route-note.md` только если результат должен быть передан другой Сущности или в другой адресный контур;
- писать `manifest.md` только если создаётся пакет или набор файлов, состав которого нужно проверять;
- писать `sha256sums.txt` для recovery-пакетов, передаваемых архивов и других случаев, где требуется проверка целостности;
- фиксировать exit codes важных команд;
- не требовать от ОПЕРАТОРА искать вывод в терминале;
- по возможности сам забирать удалённый отчёт на локальную машину;
- иметь rollback или явно указывать, почему rollback невозможен;
- не выполнять destructive action без отдельного подтверждения.

## 11. Где запускать

Каждая инструкция должна явно указывать место запуска.

Форматы:

    Запускать на ноутбуке ОПЕРАТОРА.
    Запускать на Android/Termux.
    Запускать на p552203.
    Запускать на ЭРэФии.
    Запускать на Буржуинии.
    Запускать внутри VM tera-a.
    Запускать внутри VM tera-b.

Если место запуска неизвестно, задача считается неготовой.

    /data/wellbeing/obs

Домашний каталог Сущности:

    /data/wellbeing/obs/<entity>/

    inbox

Маршрут завершается предусмотренной физической либо locator-based delivery с подтверждённым receipt требуемого объекта/версии либо фиксируется реальная причина недоставки и следующий шаг, если он нужен.

## 13. Имена файлов и пакетов

Имена файлов должны быть короткими, смысловыми и пригодными для поиска.

Для значимого артефакта, который передаётся между Сущностями, используется короткая маршрутная схема:

    <КОД_ОТПРАВИТЕЛЯ>__<смысловое-название>__<КОД_ПОЛУЧАТЕЛЯ>.<ext>

Исключение: PROMPT-файлы task conveyor не являются обычными маршрутизируемыми результатами. Их имя начинается с кода адресной Сущности и формируется только по task-conveyor canon, включая обязательный диапазон длины.

Подробные коды, обработка `UNK` и риск-маркеры определяются действующим каноном маршрутизации. Для локального рабочего файла, который никуда не маршрутизируется, маршрутные коды в имени не обязательны.

Хорошо:

    report.md
    route-note.md
    manifest.md
    install-wbn-node.sh
    verify-provodnik-gateway.sh
    request-to-sysadmin-p552203-xray-ssh.md

Плохо:

    final-final-2.md
    report-new-new.md
    202605251822331919923-x-super-long-technical-mess.md
    безымянный файл
    файл с непонятной ролью

Для пакетов допускается каталог:

    <topic>-MMDD-HHMM

Пример:

    provodnik-reboot-test-0526-1430

Внутри пакета имена файлов должны быть короткими:

    report.md
    route-note.md
    manifest.md
    sha256sums.txt

## 14. Пакеты

Пакет создаётся, когда несколько файлов образуют один проверяемый результат, должны передаваться вместе или требуется восстановимость состава.

Минимальный локальный пакет обычно содержит:

    README.md
    report.md

`manifest.md` и `sha256sums.txt` добавляются, если нужно проверять состав или целостность.

Для исполняемой задачи пакет может содержать:

    README.md
    run-task.sh
    report.md
    manifest.md        # если файлов несколько и состав важен
    sha256sums.txt     # если нужна проверка целостности

Для передачи другой Сущности добавляются только необходимые маршрутные файлы:

    task.md или рабочий артефакт
    route-note.md      # если отдельная маршрутная записка действительно нужна
    upload-task.md     # только для отдельной ручной физической доставки рабочего артефакта; не для task-conveyor PROMPT
    manifest.md        # если передаётся пакет, а не одиночный файл

Не следует добавлять `route-note`, `manifest`, `upload-task` и контрольные суммы механически. Их наличие должно отвечать конкретной функции: маршрут, состав, доставка или проверка целостности.

Если пакет создаёт архив, рядом или внутри должен быть README с точным составом и способом проверки.

## 15. Manifest

Manifest должен содержать:

- package_id;
- source_location;
- generated_files;
- recipients;
- copied_to;
- сведения о контрольной сумме или ссылка на `sha256sums.txt`, если для пакета предусмотрена проверка целостности;
- operator_action;
- unresolved_questions;
- status;
- служебный хвост.

Manifest не заменяет route-note. Manifest отвечает на вопрос “что лежит в пакете”, а route-note отвечает на вопрос “кому и что с этим делать”.

## 16. Route-note

Route-note должен содержать:

- кому;
- что передано;
- зачем;
- что сделать;
- куда вернуть ответ;
- какие файлы загрузить;
- ограничения;
- стоп-условия;
- служебный хвост.

Route-note должен быть коротким и пригодным для маршрутизации. Не надо превращать его в роман, даже если Сущности скучно.

## 17. Upload-task

`upload-task` создаётся только если реальная доставка **рабочего артефакта или результата** требует отдельного отслеживаемого шага ручной физической загрузки файла ОПЕРАТОРОМ или иным ручным механизмом.

Стандартная загрузка PROMPT-файла task conveyor в адресный Entity-чат не оформляется как `upload-task`: это отдельный механизм активации, полностью регулируемый task-conveyor canon.

Если разрешённая locator-based delivery выполнена и receipt требуемой версии подтверждён, `upload-task` не нужен.

Если файл уже фактически передан адресату в рамках текущего действия либо отдельная задача доставки не требуется, `upload-task` не создаётся.

Upload-task должен содержать:

- адресата;
- точные имена файлов;
- зачем выполнить физическую загрузку;
- что адресная Сущность должна вернуть;
- статус `upload_pending`.

Важно:
локальное копирование файла в inbox и простая внешняя публикация сами по себе не завершают адресный маршрут.

## 17.1. Состояния межсущностного артефакта и маршрута

Для значимого межсущностного результата различаются:

- **created / создан** — артефакт фактически существует;
- **published / опубликован** — артефакт размещён во внешнем доступном контуре;
- **delivered / доставлен** — выполнена адресная передача конкретному получателю;
- **received / получен** — адресат или доверенный механизм подтвердил доступ к требуемому объекту;
- **acknowledgement / подтверждение факта** — явно подтверждён конкретный факт, например receipt или проверка версии;
- **accepted / принят** — ответственная принимающая сторона содержательно приняла конкретную версию результата.

Инвариант:

`publication != delivery != receipt != acknowledgement != acceptance`.

Публикация без конкретного адресата и адресного dispatch не является delivery.

Receipt означает доступ к объекту, но не approval/acceptance его содержания.

### Два допустимых способа адресной доставки

Межсущностная доставка может завершаться:

1. фактической передачей файла адресату;
2. проверяемой locator-based delivery уже существующего артефакта.

Locator-based delivery допустима только если одновременно:

- артефакт фактически существует;
- адресат конкретно определён;
- выполнен адресный dispatch;
- locator проверяем и доступен адресату;
- для значимого объекта однозначно определена immutable version identity;
- receipt требуемой версии подтверждён;
- определён failure-mode на случай недоступности locator или несовпадения версии.

Mutable reference вроде `main` может использоваться для навигации, но для значимого результата не заменяет идентификацию конкретной версии.

Если locator недоступен или требуемая версия не подтверждена, маршрут не считается received/complete. Фиксируется реальная причина и следующий шаг только если он нужен.

Создание, публикация или доставка артефакта сами по себе не закрывают задачу, если критерий результата требует acceptance или другого терминального факта.

## 18. Автоматический отчёт

Каждый рабочий скрипт должен создавать отчёт.

Минимум:

- что делалось;
- где запускалось;
- target host или target path;
- какие команды выполнялись;
- какие проверки прошли;
- какие проверки упали;
- какие файлы созданы;
- какие данные не подтверждены;
- следующий безопасный шаг;
- статус.

Нельзя полагаться на то, что ОПЕРАТОР скопирует весь терминал. ОПЕРАТОР не является принтером логов, как бы некоторым программам этого ни хотелось.

## 19. Работа с удалёнными серверами

Скрипт, работающий с сервером, должен:

- явно указывать host;
- явно указывать user;
- явно указывать port;
- не полагаться на память ОПЕРАТОРА;
- использовать ssh/scp/rsync явно;
- писать remote report;
- по возможности забирать remote report обратно;
- не раскрывать пароль в выводе;
- не вставлять secrets в chat;
- не путать локальный sudo и удалённый sudo.

Если нужен sudo на удалённой машине:

- использовать `ssh -tt`, если требуется интерактивный ввод;
- заранее объяснить, что пароль вводится руками;
- не копировать пароль в чат;
- не пытаться выполнять remote sudo локальным sudo.

## 20. Работа с GitHub и репозиториями

В репозиторий можно публиковать:

- исходники;
- шаблоны;
- генераторы;
- документацию;
- sanitized configs;
- deployment scripts;
- verify scripts;
- README;
- policy docs.

В репозиторий нельзя публиковать:

- рабочие кошельки;
- private keys;
- seed;
- passwords;
- tokens;
- live runtime DATA целиком;
- chain DB;
- BlockChain state;
- `.ssh`;
- production config с secrets.

Перед force push, перезаписью истории или массовым удалением файлов нужно отдельное подтверждение.

## 21. Secrets и приватные данные

Нельзя публиковать или передавать в чат:

- DATA/WALLET;
- private keys;
- seed;
- password;
- token;
- DB;
- BlockChain;
- chain state;
- `.ssh`;
- приватные конфиги;
- полные production-конфиги с secrets;
- cookie/session;
- API keys.

Recovery-пакеты должны быть sanitized, то есть очищены от приватных данных.

Если Сущность не уверена, секрет это или нет, считать секретом и запросить решение.

## 22. Опасные действия

Отдельного подтверждения требуют:

- удаление VM;
- удаление qcow2;
- очистка DATA;
- удаление DB/BlockChain;
- публикация runtime-файлов;
- публикация wallet/config;
- изменение production-ноды;
- изменение firewall;
- изменение SSH-порта;
- отключение password SSH;
- force push;
- перезапись GitHub-файлов;
- массовое удаление;
- purge quarantine;
- изменение DNS;
- включение HTTPS на занятом 443;
- перенос production-сервиса;
- открытие публичного API.

Если опасное действие нужно, сначала создать plan.md и rollback.md, затем дождаться подтверждения.

## 23. Формат документов

Документ начинается с:

- краткого смысла;
- назначения;
- требуемых действий;
- статуса.

Служебные данные идут вниз:

- КТО;
- ДЛЯ ЧЕГО;
- СТАТУС;
- source;
- provenance;
- related files;
- approval status.

Нельзя начинать документ тяжёлой служебной шапкой, если это не требуется конкретным инструментом.

## 24. Время и timestamp

Сущность не должна выдумывать timestamp.

Метка времени допустима только если:

- есть утверждённый источник проектного времени;
- источник доступен;
- значение явно получено;
- в документе указано, откуда взята метка.

Если источник времени недоступен, писать:

    generated_without_trusted_project_time

или:

    project_time_source_unavailable

Не подставлять время “по ощущению”.

## 25. Статусы документов и задач

Рекомендуемые статусы:

    draft
    working
    review_required
    waiting_for_input
    waiting_for_operator
    upload_pending
    confirmed_for_execution
    executed
    failed
    archived
    monitor

Сущность не должна писать `executed`, если нет отчёта выполнения.

Сущность не должна писать `confirmed`, если нет подтверждения ОПЕРАТОРА или ответственного.

Эти статусы не являются универсальной машиной состояний для coordination field. Состояния delivery/receipt/acknowledgement/acceptance различаются отдельно по разделу 17.1 и не должны сводиться к одному полю `status`.

## 26. Правило “не имитировать исполнение”

Запрещено:

- писать “готово”, если файл не создан;
- писать “установлено”, если нет отчёта установки;
- писать “работает”, если нет health-check;
- писать “доставлено” или “получено”, если предусмотренная физическая либо locator-based delivery и соответствующий receipt реально не подтверждены;
- писать “проверено”, если проверка не выполнялась;
- писать “исправлено”, если нет подтверждения после исправления.

Допустимые формулировки:

    подготовлен файл;
    создан скрипт;
    ожидается запуск ОПЕРАТОРОМ;
    требуется отчёт;
    по предоставленному отчёту подтверждено;
    не подтверждено.

## 27. Роль ОПЕРАТОРА

ОПЕРАТОР:

- скачивает файлы из чата, когда это требуется рабочим циклом;
- запускает скрипты;
- вводит пароли руками, если нужно;
- проверяет результат глазами;
- выполняет ручную физическую доставку файлов адресным Сущностям только там, где маршрут действительно требует такого шага;
- утверждает опасные действия;
- принимает практическое применение результата.

Сущность не должна перекладывать на ОПЕРАТОРА догадки. Инструкция должна быть конкретной.

## 28. Роль КООРДИНАТОРА

КООРДИНАТОР:

- разрешает неоднозначную межконтурную маршрутизацию и зависимости;
- решает, кому какие файлы передать, когда адресат не следует однозначно из уже установленного процесса;
- собирает ответы Сущностей там, где требуется межконтурная координация;
- фиксирует решения;
- понижает или повышает приоритет хвостов в пределах утверждённых полномочий;
- переводит устаревшие источники в legacy;
- не считает inbox или публикацию конечной точкой адресного маршрута;
- не обязан быть посредником каждого прямого обмена и не создаёт новые approved-нормы собственным решением.

## 29. Роль АРХИВАРИУСА

АРХИВАРИУС:

- фиксирует документы;
- проверяет карточки;
- различает рабочий файл и временный мусор;
- связывает report, route-note, manifest и upload-task;
- помогает отличать значимые документы от следов исполнения;
- поддерживает восстановимость происхождения результата.

## 30. Роль КАНЦЕЛЯРА

КАНЦЕЛЯР:

- превращает рабочие правила в регламент;
- различает факт, предположение и предложение;
- фиксирует границы ответственности;
- готовит policy и публичные disclaimers;
- не даёт техническим черновикам притворяться внешними обязательствами.

## 31. Роль РЕДАКТОРА

РЕДАКТОР:

- переводит материалы в readable-first формат;
- очищает тяжёлые шапки;
- адаптирует текст под адресата;
- не искажает фактический статус;
- отделяет публичный текст от внутреннего runtime-мусора.

## 32. Роль профильной технической Сущности

Профильная техническая Сущность:

- сначала подтверждает данные;
- потом создаёт файл или пакет;
- указывает место запуска;
- создаёт отчёт;
- ждёт отчёт или вводные;
- не чинит работающий контур без причины;
- не трогает production без подтверждения;
- не смешивает разные роли сервера в один неуправляемый комбайн.

## 33. Работа с UI-форматами

Для производственных задач UI-блоки, canvas, writing block и длинные chat-ответы не заменяют файл.

Допустимы:

- краткое пояснение;
- визуальный черновик;
- обсуждение идеи;
- текст, который пользователь явно просит именно в чате.

Не допустимы как основной транспорт:

- значимый регламент;
- рабочий отчёт;
- маршрутный пакет;
- длинный скрипт;
- техническая инструкция;
- результат для передачи другой Сущности.
