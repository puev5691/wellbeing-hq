# Концепция движка организационной динамики

## Зачем зафиксирован этот документ

В ходе построения карты механизмов формирования коллективного субъекта ОПЕРАТОР предложил следующий шаг: превратить исследовательскую модель в алгоритм, а затем потенциально в программное ядро, которое сможет моделировать организационные процессы, показывать их динамику, использовать статистические данные для выявления векторов развития и помогать оценивать меры коррекции.

ОПЕРАТОР отдельно распорядился **не передавать задачу КОДЕРУ сейчас**. Сначала ВОЛОНТЁР должен закончить запланированную исследовательскую работу, параллельно развивая эту концепцию по мере появления новых evidence и механизмов.

Этот документ поэтому имеет статус исследовательской концепции, а не технического задания на разработку.

## 1. Исходная идея

Если механизмы коллективного субъекта удаётся описать не только словами, но и через наблюдаемые состояния, события и переходы, их можно представить как динамическую модель.

Минимальная схема:

`состояние системы(t) + события + правила перехода → состояние системы(t+1)`

Поверх неё можно рассчитывать наблюдаемые показатели, тенденции и сценарии.

Возможный будущий продукт: **ядро моделирования коллективного субъекта / движок организационной динамики**.

Его назначение не в том, чтобы «решать за коллектив», а в том, чтобы:

1. отображать фактическое состояние совместной деятельности;
2. обнаруживать структурные изменения и риски;
3. показывать направления развития показателей;
4. моделировать последствия возможных организационных вмешательств;
5. сравнивать прогноз модели с последующим фактическим результатом;
6. накапливать evidence о том, какие механизмы и меры действительно работают при определённых условиях.

## 2. Что может стать объектами модели

Рабочий перечень, который должен уточняться по мере исследования:

- участник;
- группа/коллектив;
- задача;
- функция;
- роль;
- полномочие;
- обязанность;
- ответственность;
- решение;
- действие;
- результат;
- проверка результата;
- правило;
- нарушение;
- конфликт;
- санкция;
- апелляция/коррекция;
- ресурс;
- объект совместного владения;
- вклад;
- распределение результата;
- доверие;
- обучение;
- знание/организационная память;
- локальный узел;
- федеративный уровень;
- делегирование;
- отзыв полномочия;
- вход/выход участника.

Этот список не утверждён как окончательная онтология.

## 3. Событийная модель

Система должна изменяться через фиксируемые события, а не через произвольное изменение скрытых параметров.

Примеры событий:

- создана задача;
- назначена функция;
- делегировано полномочие;
- принято решение;
- задача принята исполнителем;
- результат создан;
- результат принят/отклонён;
- срок нарушен;
- правило изменено;
- участник вошёл/вышел;
- возник конфликт;
- применена санкция;
- решение отозвано;
- проведено обучение;
- создан/изменён общий актив;
- локальный узел передал функцию федеративному уровню.

Событие должно иметь provenance и, если модель питается реальной системой, ссылку на проверяемый источник.

## 4. Три слоя данных

Критически важно не смешивать:

### Измеренное
Фактические события и данные, полученные из наблюдаемого процесса.

### Вычисленное
Показатели, однозначно рассчитанные из измеренных данных по известной формуле.

### Предсказанное
Результат модели, симуляции или статистического прогноза.

Интерфейс и данные будущей системы должны явно показывать, к какому слою относится каждое значение. Прогноз не должен незаметно превращаться в факт.

## 5. Возможные метрики

Кандидаты, не утверждённый набор:

- концентрация полномочий;
- концентрация принятия решений;
- доля задач без ответственного;
- доля решений без исполнения;
- время `постановка → результат`;
- доля результатов, прошедших независимую проверку;
- зависимость процесса от отдельных участников;
- устойчивость при выпадении узла/участника;
- разрыв между полномочиями и ответственностью;
- скорость ввода нового участника;
- полнота передачи организационной памяти;
- доля конфликтов, разрешённых установленной процедурой;
- частота отмены/коррекции ошибочных решений;
- плотность обратных связей;
- доля реально участвующих в collective-choice процедурах;
- автономность локальных узлов;
- доля общих функций, успешно выполняемых федеративным уровнем;
- динамика общего ресурса/капитала при наличии соответствующей модели;
- доля free-rider поведения, если удастся дать ему проверяемое операциональное определение.

Каждая метрика должна получить отдельное определение, формулу, источник данных, границу применимости и известные способы обмана/искажения.

## 6. Векторы развития

Под «вектором развития» в этой концепции не понимается мистический прогноз будущего.

Это наблюдаемая комбинация изменения нескольких показателей во времени, для которой существуют evidence или проверяемая гипотеза о возможном системном результате.

Примеры кандидатных паттернов:

`рост концентрации полномочий + падение участия + рост зависимости от одного узла → риск централизации/захвата управления`

`рост числа участников > способность системы обучать и включать новых → риск потери воспроизводимости`

`рост обсуждений + низкая доля завершённых задач + размытая ответственность → риск имитации коллективной субъектности без операционной способности`

Эти связи пока являются гипотезами. Для каждой потребуется empirical/evidence layer и проверка ложных срабатываний.

## 7. Два возможных режима будущей программы

### Симулятор

Пользователь задаёт начальные условия и правила, затем сравнивает сценарии.

Примеры: изменение размера группы; введение/отмена отзыва полномочий; изменение способа распределения результата; появление федеративного уровня; изменение правил санкций; потеря ключевого участника.

### Цифровой двойник живого сообщества

Модель получает реальные события рабочего процесса и поддерживает текущее вычисляемое состояние конкретного сообщества/проекта.

В этом режиме особенно важны provenance, version identity, права доступа, защита персональных данных и запрет на смешение наблюдения с прогнозом.

## 8. Контур принятия мер

Предпочтительная архитектура:

`наблюдение → диагностика → сценарный прогноз → предложение вмешательства → решение уполномоченного человека/органа → изменение → измерение результата → обновление модели`

Автоматическая скрытая коррекция поведения людей не является целью концепции.

Система должна помогать субъекту управления видеть последствия и выбирать действие, а не незаметно становиться управляющим субъектом сама.

## 9. Связь с «Благополучием»

Проект уже формирует потенциально полезный тип событийных данных:

`задача → исполнитель/Сущность → источник → решение → артефакт → проверка → статус → доставка → receipt → изменение правила/состояния`

Это делает «Благополучие» потенциальной экспериментальной площадкой для части будущей модели.

Однако существование файлов, ролей и маршрутов само по себе не доказывает, что проект уже является полноценным коллективным субъектом или что модель валидна. Это должно проверяться на реальных эпизодах, включая провалы, recovery, смену исполнителя, ошибки и повторное использование накопленного результата.

## 12. Критерий готовности к постановке разработки

Перед передачей в разработку должны существовать как минимум:

- минимальная онтология объектов;
- перечень событий;
- формальная схема состояний и переходов;
- набор измеряемых метрик с определениями;
- разделение measured/computed/predicted;
- набор подтверждённых и неподтверждённых causal hypotheses;
- failure-mode map;
- несколько исторических/реальных datasets или сценариев для проверки;
- минимальный набор unit-like behavioral cases для модели;
- правила provenance и versioning;
- границы автоматизации и человеческого решения;
- критерии, по которым симуляция считается ошибочной или недостаточной.
