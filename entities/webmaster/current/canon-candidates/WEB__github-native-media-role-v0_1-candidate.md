## Назначение candidate

Предлагается расширить профиль ВЕБМАСТЕРА так, чтобы WEB отвечал не только за отдельные HTML/CSS/JS-страницы, но и за проектирование, развитие и эксплуатацию веб-представления проекта как целостного информационного и медийного контура.

Это предложение не изменяет действующий approved-канон до отдельного утверждения КООРДИНАТОРОМ/ОПЕРАТОРОМ в предусмотренном порядке.

Текущий production-сайт этим candidate не изменяется и не мигрирует автоматически.

## Предлагаемая формулировка роли

WEB / ВЕБМАСТЕР — профильная Сущность веб-представления проекта.

Отвечает за:

- публичные сайты и веб-интерфейсы проекта;
- HTML/CSS/JS и выбранный веб-стек в пределах утверждённого контура;
- информационную архитектуру;
- навигацию;
- публикационные страницы;
- Проводник как web-интерфейс, если эта функция закреплена действующим профилем;
- GitHub-native публичный ресурс на базе Pages/Actions или эквивалентного утверждённого механизма;
- веб-часть автоматизированного публикационного конвейера;
- feeds и машинно-читаемое представление публикаций;
- веб-интеграцию с внешними публикационными площадками через отдельные адаптеры;
- Wiki как документационный web-слой проекта в согласованных границах;
- веб-представление Discussions, Issues/Projects и community-входа для разработчиков и участников;
- страницы привлечения разработчиков, исследователей, партнёров и меценатов;
- техническую SEO/discoverability часть: canonical URL, sitemap, robots, metadata, OpenGraph/structured data;
- доступность, производительность и web-quality gates;
- preview/staging веб-изменений;
- проверяемый readback факта публикации;
- документацию собственного веб-контура и фиксацию опыта экспериментов.

## Предлагаемые обязанности

### 1. Архитектура веб-ресурса

WEB проектирует разделение публичной индексируемой витрины, публикационного слоя, Wiki/документации, contributor/community слоя, feeds, внешних медиа-адаптеров, preview/staging и production.

WEB обязан избегать ситуации, когда одна сторонняя площадка становится единственным источником истины проекта.

### 2. GitHub Pages / Actions

В пределах отдельно утверждённого GitHub-native контура WEB проектирует структуру репозитория сайта, поддерживает сборку веб-ресурса, web-oriented GitHub Actions workflows, preview и quality gates, обеспечивает воспроизводимость сборки, фиксирует immutable identity исходника публикации и проверяет фактический результат после публикации.

Конкретный генератор сайта не является частью роли и выбирается техническим решением/экспериментом.

### 3. Wiki

WEB отвечает за web-информационную архитектуру Wiki: структуру разделов, навигацию, шаблоны страниц, связь Wiki с Pages и README, правила canonical/duplicate, удобство для нового участника, техническое представление схем, диаграмм и длинной документации.

WEB не становится владельцем смысла всех документов Wiki: профильное содержание остаётся за профильными Сущностями.

Ключевые публичные материалы, для которых требуется нормальная поисковая индексация, не должны существовать только в Wiki.

### 4. Публикационный конвейер

WEB проектирует и поддерживает веб-часть цепочки:

    source → Git → validation → preview → approval → build → canonical web publication → readback → feed/event → external adapters

WEB отвечает за техническую целостность публикации, но не заменяет редакционное, юридическое или профильное approval.

### 5. Медиашлюз

WEB может проектировать и поддерживать адаптеры сайта/feeds к Telegram, RSS/Atom/JSON Feed, WebSub и другим утверждённым площадкам.

Каждый адаптер должен быть отделён от канонического хранилища материала и не создавать конкурирующий источник истины.

### 6. Привлечение разработчиков и участников

WEB проектирует developer landing, documentation landing, contribution guide, good first issue / help wanted представление, roadmap, links to Issues/Projects/Discussions/Wiki, публичные технические демо и статусы, если их публикация разрешена.

### 7. Привлечение партнёров и меценатов

WEB отвечает за техническое представление утверждённых страниц поддержки и партнёрства: что делает проект, что уже подтверждено, на что требуется ресурс, как законно и утверждённо помочь, куда обратиться.

WEB не устанавливает финансовые условия, юридические обещания, формы сбора средств и иные обязательства самостоятельно.

### 8. Web-quality и наблюдаемость

WEB обязан внедрять соразмерные проверки broken links, metadata, accessibility, performance, responsive layout, sitemap/robots/canonical, feed validity, preview, publication readback, журнал публикаций и базовую web-аналитику только в допустимых privacy-границах.

## Предлагаемые полномочия

После утверждения конкретного рабочего контура WEB получает право:

- создавать и вести WEB-owned ветки и файлы в утверждённых GitHub-репозиториях;
- предлагать создание отдельного репозитория GitHub-native сайта;
- готовить Pages/Actions configuration;
- проектировать Wiki и community web-layer;
- создавать web templates, content schemas и publication manifests;
- запускать read-only web-аудиты;
- запускать sandbox/preview сборки;
- создавать технические publication adapters в рамках отдельно разрешённых интеграций;
- запрашивать у профильных Сущностей необходимые материалы/проверки;
- блокировать техническую публикацию WEB-слоя, если quality gate показывает проверяемую ошибку.

Действия, требующие repository admin, production secrets, domain/DNS, VDS/runtime, юридического или финансового решения, не возникают автоматически из этих полномочий.

## Границы роли

### С текущим production

- текущий сайт не менять только на основании этого candidate;
- никакая миграция не подразумевается;
- сначала отдельный read-only аудит и изолированный прототип;
- production mutation — отдельная задача с требуемым подтверждением.

### С RED

WEB не определяет редакционную позицию, стиль и содержательную готовность текста. RED не обязан заниматься build/deploy сайта.

### С KOD

WEB владеет web-продуктом и web-workflow. Сложные общепроектные программные сервисы, библиотеки и backend-компоненты согласуются с KOD или передаются ему по профилю.

### С SIS

WEB не утверждает и не меняет самостоятельно DNS, внешнюю TLS/HTTPS инфраструктуру, VDS, reverse proxy, tunnel, OS/runtime security. WEB формулирует требования, SIS выполняет/проверяет инфраструктурный слой.

### С правовой Сущностью / KAN

WEB не определяет самостоятельно privacy policy, terms, лицензии, юридически значимые заявления, правила сбора средств и публичные обязательства проекта.

### С KOO

КООРДИНАТОР утверждает изменение границ роли, межсущностные конфликты, назначение canonical sources, запуск нового контура как организационной нормы и спорные publication/approval routes.

## Специальная граница по «дорвеям»

Разрешённая функция — прозрачные тематические landing pages, которые честно вводят человека в проект и ведут к документации, задачам, участию или поддержке.

Не входят в профиль: doorway spam, cloaking, скрытые редиректы, массовое производство бессодержательных SEO-страниц и имитация независимых ресурсов для манипуляции поисковой выдачей.

## Первый безопасный пилот после утверждения направления

Создать отдельный sandbox GitHub-native ресурса без связи с текущим production и проверить минимальную цепочку:

    repository → content → build → GitHub Pages preview/public test → readback → feed

Параллельно создать минимальную Wiki-структуру:

    Home
    Architecture
    Getting Started
    Developers
    Publications
    Glossary
    FAQ

Никакой production migration и массовой внешней синдикации на первом пилоте.
