# ВЕБМАСТЕР в медийном контуре: синдикация и автоматизация

## 1. Архитектурный принцип

Не делать Telegram или любую другую площадку местом, где рождается канонический материал.

Канонический объект должен жить в управляемом контуре проекта и иметь устойчивый URL/ID/version. Внешние площадки получают сокращённое или адаптированное представление.

Схема:

`source -> site publication -> verified canonical URL -> event -> adapters -> external channels`

## 2. Atom feed как дешёвый универсальный слой

Atom — стандартный формат синдикации веб-контента (RFC 4287). Он подходит как базовый машиночитаемый поток публикаций.

Преимущества:

- открыт и не принадлежит соцсети;
- легко генерируется статически;
- материал имеет устойчивый id/link/updated;
- feed могут читать агрегаторы, боты и собственные сервисы проекта.

Рекомендация: генерировать Atom автоматически при build.

JSON Feed можно давать дополнительно для удобства собственных интеграций, но Atom имеет более формальный стандартный статус.

## 3. WebSub как push-слой

WebSub — W3C Recommendation, обновлённая в 2026 году. Он добавляет push-модель к web feeds: publisher сообщает hub об изменении, а hub рассылает обновление подписчикам через HTTP callbacks.

Для проекта это интереснее бесконечного polling:

`new article -> feed updated -> hub -> subscribers/adapters`

Использовать только после появления реальной потребности. На первом пилоте обычного Atom достаточно.

## 4. Telegram adapter

Telegram Bot API позволяет отправлять текстовые сообщения и изображения в канал по `chat_id`/`@channelusername` при наличии прав бота.

Адаптер должен получать уже проверенные данные публикации:

- title;
- summary;
- canonical URL;
- optional image;
- publication id.

Он не должен читать «что-нибудь последнее» из каталога и гадать, что отправлять.

Сохранять после отправки:

- `message_id`;
- target channel;
- publication id;
- source commit;
- результат API.

Это позволит делать update/correction без поиска сообщения глазами.

## 5. n8n как возможный orchestration layer

n8n имеет готовые GitHub и Telegram nodes и может быть self-hosted. Для self-hosting документация рекомендует Docker; для production доступен Docker Compose.

Что n8n может дать медийному контуру:

- webhook от GitHub/deploy;
- нормализацию payload;
- ветвление по каналам;
- Telegram publication;
- approval внутри Telegram для отдельных workflow;
- retry/error routing;
- запись результата обратно в GitHub/API.

Но n8n — отдельный сервис с собственным состоянием, credentials, обновлениями и журналами. Он полезен, когда адаптеров становится много. Для одного Telegram-канала GitHub Action или маленький Worker может быть проще и проверяемее.

## 6. ActivityPub как дальний горизонт

ActivityPub — W3C Recommendation для федеративных социальных сетей. Он определяет client-to-server и server-to-server слой; у actor есть `inbox` и `outbox`.

Для «Благополучия» это потенциально интересно как путь к собственному федеративному медийному узлу, не зависящему от одной платформы.

Но это не задача первого этапа. Сначала нужен устойчивый канонический web-поток, feed и простой adapter architecture.

## 7. Контентные варианты из одного источника

Вместо ручного копипаста один publication object может порождать:

- полную web-страницу;
- карточку для главной;
- Atom entry;
- короткий Telegram post;
- анонс для другой сети;
- OpenGraph/preview metadata;
- JSON payload для Проводника;
- будущую email/newsletter-версию.

Важно: генератор не должен самовольно менять смысл. Автоматически безопасно преобразовывать структуру и формат; смысловые сокращения/пересказы должны проходить редакционное правило.

## 8. Медиафайлы

Изображения лучше хранить с явной provenance и генерировать производные размеры автоматически. Современные framework/toolchains позволяют оптимизировать изображения на build или edge.

Для канала публикации следует передавать уже выбранный asset, а не позволять адаптеру произвольно брать «первую картинку».

## 9. Рекомендуемый рост контура

### Уровень 1
Git -> site -> Atom -> ручная проверка.

### Уровень 2
Git -> preview -> quality gates -> site -> readback -> Telegram adapter.

### Уровень 3
Несколько адаптеров + n8n/Worker orchestration + retry + centralized log.

### Уровень 4
WebSub, federated channels, возможно ActivityPub, автоматическая аналитика и feedback loop.

Так автоматизация растёт вместе с реальной нагрузкой, а не опережает её на три архитектурных революции.
