# GitHub-native веб-контур проекта — исследовательская записка WEB

## Смысл

Текущий production-сайт проекта не трогать. Параллельно спроектировать отдельный GitHub-native веб-контур, который может стать:

- публичной визитной карточкой проекта;
- серьёзным информационным ресурсом;
- каноническим источником публикаций для внешних площадок;
- входной точкой для разработчиков, исследователей, партнёров и меценатов;
- живой документационной системой;
- проверяемым Git-first контуром публикации с историей версий и автоматизацией.

Рабочий принцип: содержание и конфигурация живут в Git, публикация проходит через проверяемую сборку, а внешние каналы получают материалы уже после успешной публикации.

Термин «дорвей» здесь означает легитимную входную/посадочную страницу проекта. Поисковый спам, клоакинг, массовые мусорные страницы и иные манипулятивные SEO-практики в этот контур не входят.

## Предлагаемое разделение GitHub-слоёв

### 1. GitHub Pages — публичная витрина

Назначение:

- главная страница проекта;
- объяснение целей и принципов;
- публикации и статьи;
- страницы направлений;
- новости и обновления;
- страницы для разработчиков;
- страницы для партнёров и меценатов;
- индексируемые поисковиками материалы;
- постоянные URL;
- feeds и машинно-читаемые метаданные.

Pages должен быть публичным каноническим представлением материалов, которые должны находиться поиском и распространяться наружу.

GitHub Pages поддерживает сборку через GitHub Actions. Технологический стек генератора не фиксируется каноном; Astro является сильным кандидатом для отдельного прототипа, но выбор должен подтверждаться практической пробой.

### 2. GitHub Wiki — живая энциклопедия проекта

Назначение:

- подробная документация;
- архитектура;
- словарь и понятия;
- onboarding участников;
- инструкции разработчика;
- описание подсистем;
- история решений;
- технические руководства;
- схемы, диаграммы и длинные справочные материалы.

Wiki не должна быть единственным местом для публичного материала, который обязан хорошо индексироваться поисковиками. GitHub отдельно указывает ограничения индексации Wiki. Поэтому ключевые публичные тексты должны иметь каноническую версию на Pages, а Wiki использоваться как более глубокий документационный слой.

Нужно отдельно разработать правило: что канонично на Pages, что канонично в Wiki, а что может иметь синхронизированное представление в обоих местах без появления двух конкурирующих источников истины.

### 3. GitHub Discussions — общественный слой

Назначение:

- вопросы и ответы;
- обсуждение идей;
- объявления;
- обратная связь;
- открытые дискуссии по направлению проекта;
- предварительное обсуждение работы до превращения её в Issue.

### 4. Issues / Projects — вход в работу

Назначение:

- задачи;
- roadmap;
- задачи для новичков;
- good first issue;
- запросы помощи;
- баги;
- предложения изменений;
- прозрачное движение от идеи к работе.

Для привлечения разработчиков веб-контур должен уметь показывать не только «что мы прекрасны», но и «что можно сделать прямо сейчас».

### 5. Community-файлы — правила входа

В публичном репозитории нужны, по мере зрелости:

- README;
- CONTRIBUTING;
- CODE_OF_CONDUCT;
- SUPPORT;
- SECURITY;
- issue / pull request templates;
- понятная лицензия;
- ссылки на Wiki, Discussions, Pages и roadmap.

## Публикационный конвейер

Целевая схема:

    материал
      ↓
    Git / content source
      ↓
    schema + lint + link check + quality gates
      ↓
    preview
      ↓
    approval
      ↓
    build
      ↓
    GitHub Pages
      ↓
    readback / publication evidence
      ↓
    событие публикации
      ↓
    RSS/Atom/JSON Feed/WebSub
      ↓
    Telegram и другие адаптеры площадок

### Главный принцип

Внешняя площадка не должна быть источником истины.

Источник истины — версия материала в Git и подтверждённая публикация на каноническом сайте. Telegram, соцсети, рассылки и будущие площадки получают производные представления через отдельные адаптеры.

Это позволяет менять платформу, не перестраивая сам издательский механизм.

## Публикации как данные

Каждая публикация должна иметь структурированные метаданные, минимум:

- стабильный идентификатор;
- заголовок;
- краткое описание;
- автор/ответственная Сущность;
- статус;
- канонический URL;
- дата публикации только из допустимого проверяемого источника;
- темы/теги;
- изображение/обложка при наличии;
- язык;
- версия исходника;
- provenance;
- разрешённые каналы синдикации.

Публикационный pipeline должен быть идемпотентным: повторный запуск не создаёт дубликаты без необходимости.

## Страницы привлечения

Минимально полезные входные страницы будущего ресурса:

- «Что такое Благополучие»;
- «Что уже работает»;
- «Над чем работаем»;
- «Разработчикам»;
- «Исследователям»;
- «Стать участником»;
- «Помочь проекту»;
- «Поддержать проект»;
- «Архитектура»;
- «Документация»;
- «Wiki»;
- «Roadmap / задачи»;
- «Публикации».

Страница поддержки может рассказывать о законных и утверждённых способах помочь проекту, но WEB не определяет финансовую, юридическую или фандрайзинговую политику самостоятельно.

## Качество и безопасность

Для GitHub-native контура WEB должен проектировать:

- preview до production;
- обязательную проверку ссылок;
- HTML/Markdown validation;
- базовые accessibility-проверки;
- performance budget;
- Lighthouse/Core Web Vitals контроль;
- проверку метаданных и canonical URL;
- проверку robots/sitemap/feed;
- секреты только через штатные защищённые механизмы, не в репозитории;
- минимальные права workflow;
- разделение build и deploy;
- readback после публикации;
- журнал фактических публикаций.

Production текущего сайта остаётся отдельным контуром и не меняется этой инициативой.

## Взаимодействие Сущностей

WEB отвечает за архитектуру и исполнение веб-представления.

RED определяет редакционное качество и готовность материалов к публикации.

KOD помогает с кодом, генераторами, сложной автоматизацией и программными компонентами, выходящими за простой веб-слой.

SIS отвечает за DNS, TLS/HTTPS на внешней инфраструктуре, VDS, reverse proxy, системную безопасность и runtime-инфраструктуру.

KAN/профильная правовая Сущность проверяет юридически значимые формулировки, лицензирование, privacy/terms и публичные обязательства.

KOO утверждает межсущностные границы, канонические изменения и спорные полномочия.

OPERATOR подтверждает production-изменения и иные действия, для которых это требуется действующим каноном.

## Этапы безопасной реализации

### Этап A — проектирование
Только документация, карта слоёв, информационная архитектура, source registry, candidate полномочий WEB.

### Этап B — изолированный прототип
Новый отдельный репозиторий/ветка или иной sandbox, не связанный с текущим production. Проверить Pages, Wiki, Actions, структуру контента и preview.

### Этап C — пилот публикации
Одна тестовая публикация: Git → build → Pages → readback → feed. Без внешней массовой рассылки.

### Этап D — медиашлюз
Подключить один dry-run или тестовый адаптер, затем Telegram после отдельного подтверждения.

### Этап E — общественный вход
Wiki, Discussions, contributor pages, Issues/Projects, community profile.

### Этап F — production decision
Только после измерений и отдельного решения определить, остаётся ли GitHub-native ресурс самостоятельным контуром, становится ли основным сайтом или работает рядом с существующим.

## Короткая фиксация опыта

Идея → использовать GitHub не только как хранилище кода, а как основу публичного информационного и медийного контура.

Проба → сопоставлены Pages, Actions, Wiki, Discussions, Issues/Projects и community-механизмы GitHub с потребностями проекта.

Результат → функции естественно разделяются: Pages для публичной индексируемой витрины, Wiki для глубокой живой документации, Discussions для сообщества, Issues/Projects для входа в работу, Actions для проверяемой публикации.

Вывод → направление пригодно для серьёзного отдельного прототипа без вмешательства в текущий сайт.

Фиксация → эта записка и отдельный candidate расширения роли WEB. Production не изменён.
