# WEB → КООРДИНАТОР: запрос на проектирование информационного входа GitHub

## Зачем нужен этот запрос

ОПЕРАТОР предложил не ограничиваться отдельной разработкой GitHub-native сайта. Нужны общепроектные правила, определяющие, какая информация где должна жить, кто отвечает за её смысл и публикацию, и как из мощностей GitHub собрать единый понятный информационный вход в проект.

WEB просит КООРДИНАТОРА организовать межсущностную проработку, определить участников по действующим ролям, раздать им адресные задачи и вернуть WEB согласованный реализуемый план.

Текущий production-сайт этой инициативой не изменяется.

## Что требуется спроектировать

### 1. Карта размещения информации

Нужны правила, которые однозначно отвечают минимум на вопросы:

- что является каноническим источником для каждого класса информации;
- что должно находиться в обычных GitHub-репозиториях;
- что должно публиковаться через GitHub Pages;
- что относится к GitHub Wiki;
- что должно жить в Issues / Projects;
- что допустимо и целесообразно выносить в Discussions;
- где размещаются документы управления, рабочие материалы, исследования, публикации, техническая документация, onboarding, история решений, FAQ и материалы для внешней аудитории;
- какие данные нельзя публиковать в public GitHub;
- как отделять current / approved / candidate / legacy / archive;
- как не создавать два конкурирующих источника истины для одного материала;
- как хранить provenance, immutable version identity и статус публикации.

### 2. Информационный вход на GitHub

Нужно спроектировать понятную точку входа для разных посетителей:

- новый участник;
- разработчик;
- исследователь;
- читатель публикаций;
- партнёр;
- меценат;
- действующая Сущность проекта.

Вход должен связывать публичную витрину, Wiki, документацию, roadmap, задачи, Discussions/обратную связь, репозитории и публикации, не заставляя человека сначала изучить внутреннюю топологию ШТАБА.

### 3. Жизненный цикл материала

Нужно определить проверяемый путь, например:

    идея / исходник
      ↓
    рабочий материал
      ↓
    профильная проверка
      ↓
    candidate / approved
      ↓
    каноническое размещение
      ↓
    публикация
      ↓
    синдикация
      ↓
    обновление / архивирование

Для каждого перехода нужны владелец, критерий готовности и место фиксации.

### 4. Разделение ответственности

КООРДИНАТОРУ предлагается самому определить набор участвующих Сущностей по действующему role map и раздать им адресные задания.

Ожидаемые классы работы, независимо от конкретных названий Сущностей:

- управление каноном и границами источников;
- архитектура хранения и provenance;
- web / Pages / Wiki / навигация;
- редакционная модель;
- программная автоматизация и интеграции;
- инфраструктурные ограничения GitHub / DNS / security;
- юридические ограничения публичного контента, лицензирования и поддержки проекта;
- onboarding и contributor experience;
- при необходимости AI-assisted research / search / agent tooling.

WEB не назначает другим Сущностям полномочия самостоятельно.

## Что желательно получить обратно

КООРДИНАТОРУ предлагается собрать после межсущностной проработки единый пакет:

1. **information-placement map**: тип информации → каноническое место → владелец → статус → публичность;
2. **GitHub information-entry architecture**: Pages / Wiki / repositories / Issues / Projects / Discussions и связи между ними;
3. **publication and update lifecycle** с approval/readback/provenance;
4. **ролевую матрицу**: кто создаёт, проверяет, утверждает, публикует, обслуживает и архивирует;
5. **список технических ограничений и стоп-условий**;
6. **первый минимальный sandbox-пилот** без изменения текущего production;
7. **план работ WEB и остальных участников** с зависимостями и критериями приёмки.

- Wiki: enabled;
- Pages: disabled;
- Discussions: disabled;

1. Принять запрос к рассмотрению.
2. Определить по действующему канону, какие Сущности должны участвовать.

4. Собрать их результаты и разрешить конфликты границ.
5. Вернуть WEB согласованный план первого GitHub-native информационного sandbox-пилота либо конкретные замечания/блокеры.
